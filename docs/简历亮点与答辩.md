## 一句话把项目说清楚（自我介绍第一段用）

一个终端里的 agentic 编码助手（TypeScript、零运行时依赖）：给它一句自然语言，它会读文件、改文件、跑命令。
技术上的主线是**一条统一调用链** —— 工具、权限、沙箱、界面全部是同构的插件，内核不持有特权代码；
围绕这条链做了权限规则引擎、上下文管理、执行循环收场、子代理边界、插件分发与工程化护栏。

## 1. 事件链式中枢：内核与插件同构

> **事件链式中枢**：以「一次调用 = 一个事件」为契约，把工具、权限、沙箱、界面统一做成注册在链上的中间件，
> 按 `prepend > user > append > builtin > core` 五级权威序串成 Koa 式续体链；内核不持有任何硬编码工具表，
> 内建工具与第三方插件接口完全同构。

**为什么这么设计**：agent 类程序的天然坏形状是「一个大 if-else 把模型返回的工具名分派到各个函数」，
于是"这个动作会不会被拦、被谁拦、拦下之后发生了什么"要靠读日志猜。把每个调用点做成事件之后，
链序是**声明出来的**：`next(e)` 不调就是应答，调了就是带着改写往下走，链尾只有一处，没有第二个地方能漏。

**优势**：
- 行为可推演 —— 给定"谁注册了什么 hook"，一次调用的结果可以静态说出来，不靠运行时观测；
- 可替换 —— 换掉权限判定、换掉界面渲染，都是换一个 hook，不动内核一行；
- 内建能力不特殊化 —— 六个内建工具与第三方插件走同一条注册路径，没有"内核里那张表"可以走后门。

**追问 / 答辩**：
- **Q：为什么是 Koa 式续体而不是事件发射器（emit/listener）？**
  A：发射器是广播，没人应答的调用会**静默成功** —— 对安全判定是致命的。续体链是**有返回值**的：
  没人应答就等于走到链尾，那里只能 deny。fail-closed 需要的是"有唯一收口"，不是"广播给可能不存在的听众"。
- **Q：为什么 tier 权威序是固定的，而不是按注册顺序？**
  A：注册顺序取决于插件装载顺序，那是环境决定的 —— 同一个配置在两台机器上可能得出不同裁决。
  固定 tier 意味着**重排配置不换行为**，托管策略天然压过个人规则。
- **Q：这套东西的性能开销？**
  A：诚实答：链上每次调用多几层函数调用，相对一次模型请求（几百毫秒到几秒）可以忽略；
  我们没有做基准测试，也不该拿它当卖点 —— 卖点是可推演和可替换，不是快。

## 2. 声明式权限规则引擎

> **权限规则引擎**：五层来源（user / project / local / flag / policy）逐字段合并而非整体替换；
> 规则支持工具级与「`:` 为 token 边界」的命令前缀、路径 glob 两种匹配；裁决按 `deny > ask > allow`
> 取最严、与规则写在哪一层无关，托管策略在下游放宽时**持有裁决**可推翻。

**为什么这么设计**：权限配置的经典事故是"谁都以为自己写的那条最严"，于是把裁决做成**取最严的偏序**，
而不是"后来的覆盖先来的"。另一个坑是 `:*` 被当成通配符用 —— 写成 `Bash(git push:*)` 却要求命令里真有冒号，
规则安静地永不命中；这里把 `:` 明确定义为 **token 边界**，并在启动时对不支持的写法警告一次。

**优势**：
- 配置可重排 —— 个人怎么写规则都掀不翻托管策略，这一点是**结构**，不是文档约定；
- 判定可解释 —— `/permissions` 直接打出每条规则来自哪一层、哪些工具被隐藏；
- 匹配语义有边界说明 —— 前缀匹配不懂 shell 语法（`true && git push` 绕得过去），
  所以它的定位是「给手滑与误操作加一道闸」，不吹成对抗手段。

**追问 / 答辩**：
- **Q：五层来源为什么是"逐字段合并"？**
  A：整体替换会让"项目级只想改一个 model 名"变成"必须把用户级那份抄一遍"。
  逐字段合并的代价是**同一份配置要在两处维护同一个字段**时得想清楚哪层赢 —— 我们用固定的优先级把它钉死。
- **Q：怎么防住"配置里放 `allow: ['Bash']` 一把梭"？**
  A：不防，但要它可见 —— 个人规则最严也只到 allow，托管策略里的 deny 一条都掀不翻；
  而且沙箱（见下）根本不看 allow。
- **Q：为什么 `policy` 这一层刻意没有环境变量来源？**
  A：一个环境变量就能改掉权限，等于在规则引擎上开个后门。托管策略必须来自文件或由文件派生的
  MDM 通道（注册表 / 托管偏好域 / 平台默认文件）。

## 3. fail-closed 默认安全

> **fail-closed 默认安全**：确认链走到链尾无人应答即 `deny`，非 TTY（管道、CI）默认拒绝，
> 不认识的工具拒绝，覆盖写前必须先读；**刻意不提供**任何 `--yes` 自动放行开关，
> 并把这条偏好写成 CI 里可校验的规则。

**为什么这么设计**：安全方向的错只有一边可以修。fail-open 的错（该拦没拦）在事故前不可见，
攒够了才发现；fail-closed 的错（该放没放）当场就有人喊。所以每个"没人在场"的分支都倒向拒绝。

**优势**：
- 非交互场景天生安全 —— 拿它写脚本只能做只读的活，不需要用户理解这套设计；
- 拒绝是**可解释的**：谁拒的、理由是什么都在屏幕上，不是一句"操作失败"；
- 这条偏好被写进 CI 校验器：想在流水线里加 `--yes` 这种自动放行开关，会直接红。

**追问 / 答辩**：
- **Q：非 TTY 下拒绝，那自动化怎么用？**
  A：只读的活照跑（`Read` / `Glob` / `Grep` 不加门控）。要它写盘就得有交互。
  这是**有意**把"无人值守自动改代码"排除在外 —— 加自动放行开关与这条线正面冲突：
  *谁加自动放行开关谁就是在开倒车。*
- **Q：链尾无人应答 = deny，会不会太严？**
  A：恰恰相反，这是唯一安全的默认。链尾那一处是**唯一**的收口，如果它 allow，
  那么任何一个"忘了注册 hook"的新工具都是静默放行。

## 4. 命令沙箱的位置

> **命令沙箱**：`Bash` 在真正 `spawn` 之前过一道路径闸，位置在权限链的**下游** ——
> 任何 `allow` 规则都绕不过它；`deny` 各层取并集、`allow` 只有托管层能设；
> 默认关闭，开启后同样明说"它是文本分析，不是 shell 解析器"。

**为什么这么设计**：「个人规则掀不翻托管策略」如果只是文档里的一句话，那它就是一句承诺；
把它做成**位置**（沙箱判定发生在权限链之后、起进程之前），它就变成了推论。

**优势**：
- 免于"放行开关"的侵蚀：不做 `dangerouslyDisableSandbox` —— 那个键就是一个放行开关；
- 与权限系统职责分开：权限答"要不要动手"，沙箱答"能不能碰这个路径"；
- 明确的边界声明：`x=/etc/passwd; rm $x`、`rm $(echo /etc/passwd)` 都绕得过去，
  所以它**不是**"可以放开权限"的理由。

**追问 / 答辩**：
- **Q：既然能绕过去，为什么还做？**
  A：拦的是误操作与手滑（占绝大多数），不是对抗。把它说清楚比把它吹大更有价值 ——
  标定边界的守卫能用，标定不清的守卫会给人虚假安全感。
- **Q：为什么只盖 `Bash`？**
  A：写盘的另外两条路（`Write` / `Edit`）走的是"先读过才能覆盖"与单文件确认，
  路径语义清楚、不需要切 token 猜。先把语义最糊的那条盖住，比四不像地全盖一遍好。

## 5. 上下文管理

> **上下文管理**：系统提示**每一轮重算**（会话中途改指令文件当场生效、压缩后注入面重新求值）；
> `/context` 账本按「系统提示 + 工具清单 + 会话消息」三段核算；压缩做成**变换缝**而不是闸门 ——
> 压不成就不压、出声、原文一条不动，并配「失败 3 次 / 连压 3 次仍超阈值」两道断电器。

**为什么这么设计**：上下文是 agent 的**唯一**稀缺资源，但它有三个不同的消费者（请求、用户、
诊断），三处口径不一致就会出现"用户以为还有空间、实际早就超了"。所以：一份账本，三段合计；
而压缩这个动作最容易做成"坏了也假装没事"—— 我们的原则是**压不成就别压**，
把失败说出来，而不是交一份悄悄变短的上下文。

**优势**：
- 账本对得上 —— 合计就是请求里真有的那三样之和，每段可逐项核对（工具那一行逐工具列出，不截断）；
- 压缩可恢复、可停手 —— 断电器会明说怎么恢复（手动 `/compact`、调大阈值、关掉自动压缩）；
- 注入面新鲜 —— 每轮重算的代价是几次文件读，换来的是"改了 `AGENTS.md` 立刻生效"。

**追问 / 答辩**：
- **Q：每轮重算系统提示，token 账不会抖吗？**
  A：会 —— 这是**明确记进已知限制**的代价：系统提示的字节数可能在会话中途变化。
  选择它是因为注入面过期导致的错（模型按旧规矩办事）比账本抖动严重得多。
- **Q：压缩之后 `--resume` 接回来的是什么？**
  A：盘上那份**一个字没动**（`reseed` 重置的是落盘游标，不是文件）——
  resume 接回的是完整历史；压缩只影响内存里下一轮发出去的上下文。
  这里有个真踩过的坑：数组被改短时游标必须同时归零，否则新消息会**静默不落盘**。
- **Q：阈值怎么定的？**
  A：诚实答：默认值是猜的（引擎内部看不见模型的真实窗口），自动压缩默认**关**，
  手上可控的方式永远是手动 `/compact`。把没依据的数标成没依据的，比给个假精确好。

## 6. 执行循环的收场

> **执行循环收场**：把「模型说完了」与「一轮该怎么停」分成**两层停止原因**
> （端点级枚举收敛为 7 个产品级字面量）；输出被长度上限截断时自动续写（≤3 次，每次出声）、
> 一步空产出重提示一次、流中断保留已显示的半句；一次性模式退出码走**白名单**（0 / 130 / 其余 1）。

**为什么这么设计**：agent 循环最像工程问题的地方不是"怎么调模型"，而是**什么时候停**。
把端点的停止原因原样透出，上层（界面、退出码、子代理）就得各自处理一遍 7 种以上的分支；
收敛成产品级枚举之后，"这一轮算成功吗"只有一个判断点。

**优势**：
- 不静默消费用户的额度：续写每次打一行通知（每次都真的是**一次模型请求**，会花钱）；
- 半截结果不外流：`deepcode "写一份长报告" && 下一步` 不会带着半句往下走；
- 屏幕与转录不打架：流到一半断了，屏幕上显示过的那半句**留在转录里**，再加一行失败说明。

**追问 / 答辩**：
- **Q：为什么用退出码白名单而不是黑名单？**
  A：黑名单要求"枚举所有失败"—— 新加一种失败就会漏成成功（0）。白名单只要求"枚举所有成功"，
  漏掉的那一个落进 `1`，是安全的错。
- **Q：续写上限 3 是怎么来的？**
  A：诚实答：是定的，不是测出来的（写在注释与设计文档里）。它的作用是**保险丝**：
  防止一个持续截断的模型把额度吸干，而不是宣称"接 3 次就够"。

## 7. 工具清单的唯一算法

> **工具清单唯一算法**：注册面经「本轮白名单 / 规则隐藏 / 是否有注册描述」三道过滤，
> 得出模型这一轮真正可见的工具；模型请求、`/help`、`/context` 账本三个消费者**共用同一个函数**；
> 「隐身」（策略不让露面）与「故障」（插件没注册描述）分列，各自带原因。

**为什么这么设计**：改造前三个消费者各算各的：请求里发了 6 个工具、`/help` 打的是注册面、
账本压根没算工具 —— 实测某一轮真实请求约 448 token，账本报 11（工具占真实请求的 97.5%，
账本连 2.5% 都没到）。**同一个事实有三个版本**，是这类系统的典型病症。

**优势**：
- 口径唯一 —— "在列表里" 与 "能跑" 不再是两件事；
- 故障与设计分得开 —— 插件没注册描述是**故障**（要 warn），被规则隐藏是**策略**（只 debug），
  三句措辞本身就是判据，测试钉的就是它们；
- 每个工具可追责 —— 能看到它来自哪个插件。

**追问 / 答辩**：
- **Q：为什么 `/context` 里工具那一行不截断？**
  A：账本的全部意义是**不编**。截断就得再编一句"还有 N 个没显示"，而 N 本身也可能是估的。
  `/tools` 那边相反 —— 它给的是给人读的列表，截 80 字符并在同一屏说明"模型拿到的是完整的"。
- **Q：这个重构怎么保证没改行为？**
  A：先写探针把改造前的事实**量出来**（三个消费者的三份数字），再让它们收敛到同一个函数，
  逐条对比。这也是这个项目的固定做法：不靠读代码猜，靠探针量。

## 8. 子代理的边界下沉内核

> **子代理边界下沉内核**：用「面栈 + 名字栈」按**当前这一轮**计算子代理的工具面 ——
> 省略工具声明 = 继承父级这一轮的面，给出声明 = 在该面内**求交**（只能更小）；
> 深度上限与拒绝理由一并由内核给出、结果用**判别式联合**表达（`{ok:false, reason}`）；
> `Task` 路径与第三方插件直接调用同一名词，走同一行判定。

**为什么这么设计**：改造前边界是**调用方按"会话的全部"算**的 —— 边界画在插件里，
于是嵌套一层就把父级被扣掉的面拿了回来（实测：外层看见 2 个工具，内层看见 8 个 = 会话全部）；
深度保险丝也只装在 `Task` 那条路径上，第三方插件直接递归抵达 6 层 / 13 次模型请求。
**"边界"只要不在内核里，就总有第二条路绕过去**。

**优势**：
- 一处判定，所有路径生效 —— 换路径不再等于换规则；
- 表达能力匹配现实：拒绝不再是"异常"或"空字符串"，而是结果类型里的一个分支，消费方按 `ok` 分支；
- 派生的可观测性：`agent.spawn` 事件带 `depth`，进度通知由**内核事件**驱动 →
  被拒的那次不出声（不产生"永远不回来的假账"），插件直派的子代理也被照亮。

**追问 / 答辩**：
- **Q：`tools` 从"绝对白名单"变成"父面的子集"，这不是弱化了吗？**
  A：是**收紧**：以前一个写着 `tools: ['Bash']` 的子代理，只要父级那一轮看不见 `Bash` 也拿得到；
  现在拿到的是空面。代价写进已知限制（这是本阶段唯一一处可能让人"咦"一下的行为变化）。
- **Q：深度上限为什么是 3？**
  A：保险丝而不是策略 —— 一次失控的递归要花真钱。数字是定的，理由写进代码注释。
- **Q：怎么证明"所有路径"真的都被盖住了？**
  A：两条探针各自转成**长期用例**：一条走 `Task` 路径测第四层被拒，一条让第三方插件直接递归。
  反向验证也做了 —— 把内核里那段深度判定删掉，两条一起红（3 红 / 15 绿），说明断言不是摆设。

## 9. 插件系统与分发

> **插件系统与分发**：插件清单校验 + 目录发现 + 准入闸门，classic 钩子桥接六个事件；
> 第三方插件**只能拧紧**（座位强制 `append`、放行判定一律剥掉、`uses` 越界整个插件不装）；
> 分发只做本地 marketplace 索引，且**装 ≠ 启用**（安装落点不参与自动装载，启用只认用户级设置）。

**为什么这么设计**：插件系统的核心问题是**信任边界**：第三方代码进来之后，
它能不能把安全判定放松？这里把答案做成结构而不是约定 —— 它的返回判定连它自己那一层都出不去
（`allow` 会被剥掉），座位固定在 `append`（内层），注册的事件必须在清单的 `uses` 里声明。

**优势**：
- 信任面可枚举 —— 一个插件能说上话的事件、能返回的判定，在装载期就能列全；
- 供应链克制 —— 没有网络、没有签名与校验和就不假装有；升级 = 删掉再装，不做假的版本解析；
- 「装 ≠ 启用」堵住了一个具体攻击：一个克隆下来的仓库不能按名字点亮你全局装着的插件。

**追问 / 答辩**：
- **Q：怎么防"插件在 `PreToolUse` 上返回 allow 把 deny 顶掉"？**
  A：`allow` 一律被剥掉；能返回的判定只有更严的那些。这不是"检查一下"，是**结构上到不了**。
- **Q：`uses` 只在事件级校验，是不是太粗？**
  A：是，这条**如实记进已知限制**：声明了 `tool.check` 的插件对每个工具都能说上话，
  细到 matcher 一级的声明没做。它的定位是"减少误伤面"，不是隔离机制。
- **Q：一个写坏的规则文件会怎样？**
  A：fail-closed：`PreToolUse` 上出错就翻成 `deny`（`Write` / `Edit` / `Bash` 会全停直到修好）；
  另外三个事件上没有可拦的动作，只是一句 notice。参考实现的钩子出错永远 `exit(0)`，
  我们**不接受**那个方向：一个读不懂自己规则的守卫，比一个假装没事的守卫危险。

## 10. 内建能力 mod 化

> **内建能力 mod 化**：权限裁决、指令文件、遥测、diff 四个内建模块走与第三方**完全相同**的接口注册，
> 只由 CLI 代挑座位；mod 独有「可选依赖」预检（例如缺 `git` 就不装载、启动时出声并降级到内置应答），
> 并保证同一条命令不出现两条应答者。

**为什么这么设计**：内建能力最容易变成内核里的特权分支（"这是内置的，可以直接调"）。
把它们按同一条注册路径外置，换来的是：内建与第三方**能被同一套规则检查**，
而且内建模块自己坏了也只是"少一块 + 出声"，不会拖垮进程。

**优势**：
- 降级可见 —— 缺依赖的打一行人话（`内建 mod diff 没装：这台机器上没有 git。`），
  而不是安静地少一块功能；
- 不重复应答 —— mod 装上了 CLI 就不注册自己那条回退，避免同一命令打两遍；
- 边界可强制 —— `pnpm lint` 检查 mod 只许 import `node:` 内建、契约层与自身目录，
  反过来只有 CLI 层许 import mod。

**追问 / 答辩**：
- **Q：为什么要"可选依赖"这一层，不能启动后报错吗？**
  A：启动后才发现意味着用户已经进来了、界面已经开始了；预检让"这个功能今天不在"
  在一开始就说清楚，且不装它比装作装了更安全。
- **Q：内建模块和第三方插件真的同构吗？**
  A：注册路径、事件契约、判定规则完全相同；差别只有两处，都是**更受约束**的方向：
  CLI 代挑座位（内建可以落 `prepend`/`builtin`，第三方只能是 `append`）与可选依赖预检。

## 11. 终端渲染与输出契约

> **终端渲染**：逐行纯文本流（不占整屏、可 `tee`、可滚回），markdown 做一个**子集**的行内增强，
> 认不出的语法原样保留、代码块逐字节保真；非 TTY 下输出**逐字节**与"没有这个界面"相同，
> 颜色由 `NO_COLOR` / `FORCE_COLOR` / 是否 TTY 三者决定。

**为什么这么设计**：CLI 的界面改动最容易破坏**可组合性**（管道、日志、diff）。所以把
"非 TTY 输出逐字节不变"当成承重墙：活动行与 spinner 只往 stderr 写，非 TTY 下一律不产出。

**优势**：
- 可组合 —— `deepcode ... | tee`、CI 日志、重定向全部照常；
- 装饰不吞字 —— 渲染器认不出的语法原样留着，代码块与行内代码逐字节保真；
- 可测试 —— 因为"关掉着色"与"根本没有这个功能"逐字节相同，断言可以直接比字节。

**追问 / 答辩**：
- **Q：为什么不做整屏 TUI / 语法高亮？**
  A：逐行流能进管道、能被滚回、能被复制，而整屏应用不能；这不是能力问题，是**取舍**：
  现在这个阶段可组合性更重要，所以如实写进已知限制。
- **Q：文档里渲染出来的内容与屏幕不一致怎么办？**
  A：不允许 —— 转录不许比屏幕少东西：模型流到一半断了，屏幕上显示过的半句也会落在转录里。

## 12. 工程护栏：边界由脚本守

> **工程护栏**：`pnpm lint` 里两个自写校验器强制「依赖边界」（`contract/` 零 import、
> 各层只许向下依赖）与「CI 工作流硬化」（H1–H7：第三方 action 钉 40 位 SHA、显式最小 token 权限、
> 禁 `pull_request_target`、checkout 不落凭据、出口白名单 enforce）；零运行时依赖，71 个文件 1187 条用例。

**为什么这么设计**：架构约束写进文档靠自觉，改三个月就散了。把它变成脚本之后，
"越界"这个行为会在本地 `pnpm lint` 与 CI 上同时红 —— **约束的成本从"记得"变成"改不动"**。

**优势**：
- 边界可回归 —— 往契约层加一个 import，直接红；
- 供应链硬化可执行 —— action 按 commit SHA 锁（tag 会被上游重指）、token 最小权限、
  `persist-credentials: false`（否则 token 写进 `.git/config`，后面任何一步都能拿去推东西）；
- 不引依赖做这两件事 —— 校验器是手写的文本扫描（两个文件加起来约 460 行），并把**它看不见的东西**
  （动态拼的 `uses:`、YAML 锚点）写在文件头：尽力而为的护栏，不假装是完备证明。

**追问 / 答辩**：
- **Q：为什么不用 ESLint 的 import 规则？**
  A：试过权衡：flat config 下 `import/no-restricted-paths` 支持不稳定，而这里要的只是
  "某目录不许 import"，手写脚本反而更清楚，还顺便覆盖了 `tsc` 看不见的 `.mjs`（插件源码）。
- **Q：为什么 CI 里那个跑真引擎的 job 默认跳过？**
  A：它需要防火墙 runner，而"永远红的流水线等于没有流水线"——
  所以它由仓库变量显式打开，默认不跑，跑的时候验的是"非 TTY 下没人能确认 → 拒绝"这条 fail-closed。

## 13. 反向验证：把实现改坏，看断言红不红

> **反向验证**：每个阶段的出口标准里预登记"改坏哪一处、哪条断言应该红"，
> 然后真的把实现改坏一次跑一遍；不红就说明那条断言是**摆设**，修的是断言本身。

**为什么这么设计**：测试全绿有两种可能 —— 实现是对的，或者断言根本没在测东西。
区分这两者只有一个办法：主动把实现弄错，看测试有没有意见。

**优势**：
- 断言的有效性可验证，而不是"覆盖率很高"这种间接证据；
- 改坏的**红法**本身是证据：比如把内层的工具面改回"会话全部"时，三条断言一起红
  （同一件事的三个面），说明这三条确实咬在同一处；
- 这套做法在文档里留痕：每个阶段的设计文档与变更记录里都有"改坏什么 → 实测几红几绿"的表。

**追问 / 答辩**：
- **Q：举个具体的例子。**
  A：P10 做了三条：① 把子代理的父面改回会话注册面 → 3 红 / 4 绿；
  ② 把内核里的深度判定删掉 → 3 红 / 15 绿（连既有用例一起红）；
  ③ 让 `allow` 不做交集 → 1 红 / 6 绿（只有那一条不可替代的断言发力）。三条都先红在指定位置，随后还原复绿。
- **Q：这不就是变异测试吗？**
  A：同源思想，但**手工且便宜**：不铺工具链，只在阶段收口时挑几处承重的实现改坏。
  对个人项目来说，关键是**养成"红过一次"的习惯**，而不是把变异覆盖率跑高。

## 答辩通用三问（几乎一定会被问）

**Q：这个项目最难的地方是什么？**
A：不是调模型，是**边界**。举两个真事：① 子代理的工具面原来由调用方按"会话的全部"算，
一旦嵌套就从插件里漏出去 —— 修法不是打补丁，而是把"面"按**当前这一轮**在内核里算；
② 深度保险丝原来只装在 `Task` 那条路径上，第三方插件直接递归就绕过去了 ——
所以"上限"和"面"必须落在**同一处判定**上。这类问题的共同点是：**边界只要不在内核里，就总有第二条路**。

**Q：如果重做，你会改什么？**
A：三条，都是明写着的：① 事件目录里已声明未实现的那 19 个（41 声明 / 22 实现）——
入口太多会让"这个事件到底谁应答"变糊，我会先砍到真正需要的那些；
② 权限规则的匹配语义（前缀匹配不懂 shell 语法）—— 要么老实标成"仅防手滑"，要么把 token 化做到底；
③ 上下文压缩的阈值与断电器数字都是抄来的，重做时至少要有一次真实测量。

**Q：你怎么保证质量？**
A：三层：**结构**（边界由脚本强制，越界直接红）、**断言**（把实现改坏验证测试真会红）、
**文档**（每个阶段的出口标准、偏差、"我们定的数"全部留痕，包括做不到的和做得不漂亮的）。
最后一条尤其重要：一个项目的可信度不来自它宣称支持什么，而来自它**把不确定的部分标成不确定**。

## 简历上不要写的东西

- 任何性能 / 吞吐 / 延迟数字 —— 我们没测过；
- 任何用户数、star 数、"生产可用" —— 这个项目是单人仓库，没有线上；
- "支持并发子代理" —— 已知限制里写着：并发 `spawn` 会让面栈错位，今天工具调用是串行的，这条路径不可达；
- "事件驱动高可用" 这类套话 —— 它是一条单进程的链，不是一个分布式系统；
- 把 `41 个事件` 写成 `41 个已实现` —— 事实是 41 声明 / 22 实现，其余用到时抛 `NotImplementedError`
  （这条写在面试里反而是加分项：标出"还没做"比装作做完了可信）。
