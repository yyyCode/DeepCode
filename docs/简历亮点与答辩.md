## 一句话（自我介绍第一段）

一个终端里的 agentic 编码助手（TypeScript、Node ≥ 20、零运行时依赖）：给它一句自然语言，
它会读文件、改文件、跑命令。技术主线是**一条统一调用链** —— 工具、权限、沙箱、界面是同构的插件，
内核不持有任何特权代码；可推演、可替换、fail-closed 是这条链的三条副作用。

## 1. 事件链内核：一次调用 = 一个事件，内核与插件同构

**事件链内核**：把每个调用点做成一条可注册的链 —— 工具、权限、沙箱、界面全部是插件，按
`prepend > user > append > builtin > core` 五级 tier 权威序串成 Koa 式续体链（`next(e)` 是续体，
不是事件发射器）。六个内建工具与第三方插件走**完全相同**的注册接口，内核里没有一张硬编码工具表；
链尾只有一处，没有第二个地方能漏。依赖边界由自写校验器强制（`contract/` 零 import），越界直接红。

**为什么这么设计**：agent 程序的天然坏形状是"一个大 if-else 把工具名分派到各函数"，
于是"这个动作会不会被拦、被谁拦、拦下之后发生了什么"只能靠读日志猜。做成链之后，给定注册表，
一次调用的结果**可以静态说出来**。

**优势**：行为可推演；换掉权限判定/界面渲染只是换一个 hook，不动内核；内建能力没有后门可走。
**代价**（面试里主动讲）：链上多几层函数调用，相对一次模型请求可忽略 —— 但**这条没有基准数字**，
我们没测过，卖点是可推演与可替换，不是快。

**追问**：
- **Q：为什么是续体而不是事件发射器？** 发射器是广播，没人应答的调用会**静默成功** —— 对安全判定是致命的。
  续体链有返回值，没人应答就走到链尾，那里只能 deny。fail-closed 需要的是"唯一收口"，不是"广播给可能不存在的听众"。
- **Q：为什么 tier 权威序固定，不按注册顺序？** 注册顺序由插件装载顺序决定，那取决于环境 ——
  同一份配置在两台机器上可能得出不同裁决。固定 tier 意味着**重排配置不换行为**。

## 2. 权限规则引擎：五层来源、最严裁决、托管持裁决

**权限规则引擎**：五层来源（user / project / local / flag / policy）**逐字段合并**而非整体替换；
规则支持工具级、命令前缀（`Bash(git push:*)`，`:` 是 **token 边界**而非通配符）与路径 glob
（`Read(~/.ssh/**)`）三种形态；裁决按 `deny > ask > allow` 取最严，与规则写在哪一层、排第几都无关。
托管策略在链尾**持有裁决** —— 下游若把更严的判定放宽，直接拿策略原文推翻。

**为什么这么设计**：权限事故的经典形状是"谁都以为自己那条最严"。把裁决做成取最严的偏序，
并让"个人规则掀不翻托管策略"成为**位置**（托管判定在链尾）而不是文档里的一句承诺。
另一个坑是 `:*` 被当通配符 —— 写成 `Bash(git push:*)` 却要求命令里真有冒号，规则安静地永不命中；
这里把 `:` 定成 token 边界，对不支持的写法启动时警告一次。

**优势**：配置可重排、判定可解释（`/permissions` 打出每条规则的来源层与隐藏了哪些工具）、
匹配语义的边界写在脸上（前缀匹配不懂 shell 语法，`true && git push` 绕得过去 ——
定位是"给手滑加的一道闸"，不吹成对抗手段）。

**追问**：
- **Q：`policy` 为什么刻意没有环境变量来源？** 一个环境变量就能改掉权限，等于在规则引擎上开后门。
  托管策略必须来自文件或由文件派生的 MDM 通道（Windows 注册表 / macOS 托管偏好域 / 平台默认文件）。
- **Q：五层为什么逐字段合并？** 整体替换会让"项目级只想改一个 model 名"变成"必须抄一遍用户级"。
  代价是同一字段在两处都要维护时得想清楚谁赢 —— 用固定优先级钉死。

## 3. fail-closed 默认安全：把偏好做成 CI 可校验的规则

**fail-closed 安全底线**：`tool.check` 走到链尾无人应答即 `deny`；非 TTY（管道、CI）默认拒绝；
不认识的工具拒绝；`Write` 覆盖已有文件前必须在本次会话里先 `Read` 过它。**刻意不提供**任何自动放行开关
（`--yes` 已被移除），并把这条偏好写进 CI 工作流校验器 —— 流水线里出现 `--yes` /
`--dangerously-skip-permissions` 直接红。

**为什么这么设计**：安全方向的错只有一边能修。fail-open 的错（该拦没拦）在事故前不可见，
攒够了才发现；fail-closed 的错（该放没放）当场就有人喊。所以每个"没人在场"的分支都倒向拒绝。

**优势**：非交互场景天生安全（拿它写脚本只能做只读的活）；拒绝**可解释**，屏幕上说得清谁拒的、为什么；
"不许有放行开关"不是口头纪律，是一条会红的检查。

**追问**：
- **Q：非 TTY 下拒绝，自动化怎么用？** 只读的活照跑。要它写盘就得有交互 —— 这是**有意**把
  "无人值守自动改代码"排除在外：*谁加自动放行开关谁就是在开倒车。*
- **Q：为什么未知工具是拒绝而不是报错跳过？** 链尾是**唯一**的收口；如果那个默认是放行，
  任何一个"忘了注册 hook"的新工具都是静默放行。

## 4. 命令沙箱：判定发生在权限链下游

**命令沙箱**：`Bash` 在真正 `spawn` 之前过一道路径闸（候选路径从命令行切 token 提取），
位置在权限链的**下游** —— 任何 `allow` 规则都绕不过它；`deny` 各层取并集、`allow` 只有托管层能设，
个人写了会被丢弃并出声；默认关闭，且**不做** `dangerouslyDisableSandbox`（那个键就是一个放行开关）。

**为什么这么设计**：「个人规则掀不翻托管策略」如果只是一句话，它就是承诺；把沙箱放在权限判定之后、
起进程之前，它就变成**推论**。职责也分得开：权限答"要不要动手"，沙箱答"能不能碰这个路径"。

**优势**：免于"放行开关"的侵蚀；与权限系统互不替代（`Read` / `Write` / `Edit` 不在这道闸里，
它们走"先读过才能覆盖"与单文件确认）。
**代价**（主动讲）：它是**文本分析，不是 shell 解析器** —— `x=/etc/passwd; rm $x` 绕得过去，
路径比较区分大小写，准确率靠一组手写 fixture 兜着（"我们信这组 fixture，不是我们量过"）。

**追问**：
- **Q：能绕过去为什么还做？** 拦的是误操作与手滑（绝大多数），不是对抗。
  把它标定清楚比吹大更有价值 —— 标定不清的守卫会给人虚假安全感。
- **Q：为什么只盖 `Bash`？** 写盘另外两条路走的是"先读过才能覆盖"与单文件确认，路径语义清楚、
  不需要切 token 猜。先把语义最糊的那条盖住。

## 5. 上下文管理：每轮重算 + 三段账本 + 变换缝式压缩

**上下文管理**：系统提示**每一轮重算**（会话中途改 `AGENTS.md` 当场生效，压缩后注入面重新求值）；
`/context` 账本按「系统提示 + 工具清单 + 会话消息」三段核算，工具那一行逐工具列出**不截断**；
压缩做成**变换缝**而不是闸门 —— 摘要失败 / 返回空 / 压完反而更长，三种情况都**不压缩**、出声、
原文一条不动，另配两道断电器（连续失败 3 次停手、连压 3 次仍超阈值停手，并说清怎么恢复）。
改造前实测：账本报 11 token，而同一轮真切出去的请求约 **448 token**（6 个工具的 schema 占 **97.5%**，
账本一个字都没算）。

**为什么这么设计**：上下文是 agent 唯一的稀缺资源，却有三个消费者（请求、用户、诊断）——
三处口径不一致就会出现"用户以为还有空间、其实早超了"（上面那 448 / 11 就是这个病）。
压缩这个动作最容易做成"坏了也假装没事"，我们的原则是**压不成就别压**。

**优势**：账本合计就是请求里真有的三样之和、每段可逐项核对；压缩失败可见、可停手、可恢复；
注入面永远是新鲜的。
**代价**：阈值 `compact.atTokens` 默认 100_000 是**猜的**（引擎看不见模型真实窗口），
所以自动压缩默认**关**，手上可控的永远是手动 `/compact`。

**追问**：
- **Q：每轮重算，token 账不会抖吗？** 会 —— 明确记进已知限制（系统提示字节可能在会话中途变化）。
  选择它是因为"注入面过期"（模型按旧规矩办事）比账本抖动严重得多。
- **Q：压缩之后 `--resume` 接回来的是什么？** 盘上那份**一个字没动**（`reseed` 重置的是落盘游标，
  不是文件），resume 接回完整历史；压缩只影响内存里下一轮发出去的东西。这里真踩过坑：
  数组被改短时游标必须同时归零，否则新消息会**静默不落盘**、而转录看上去一切正常。

## 6. 执行循环的收场：两层停止原因、续写、白名单退出码

**执行循环收场**：把「模型说完了」与「一轮该怎么停」分成**两层** —— 端点级停止枚举收敛为
7 个产品级字面量（上层只处理产品级，不再各处理一遍端点差异）；输出被长度上限截断时自动续写
（≤3 次，**每次出声**，每次都是真的一次模型请求）；一步空产出重提示一次；流中断保留已显示的半句
（转录不许比屏幕少东西）。一次性模式退出码走**白名单**：0 / `Ctrl-C` 130 / 其余一律 1。

**为什么这么设计**：agent 循环最像工程问题的地方不是"怎么调模型"，而是**什么时候停**。
停止原因原样透出，界面、退出码、子代理就得各自处理 7 种以上分支；收敛之后"这一轮算成功吗"
只有一个判断点。退出码用白名单而不是黑名单，是因为黑名单要求枚举**所有失败**，
新加一种失败就会漏成 0；白名单只要求枚举成功，漏掉的那个落进 1，是安全的错。

**优势**：不静默花钱（续写每次都是一次请求，每次打一行通知）；半截结果不外流
（`deepcode "写一份长报告" && 下一步` 不会带着半句往下走）；屏幕与转录不打架。

**追问**：
- **Q：续写上限 3 怎么来的？** 诚实答：是**定的，不是测出来的**（写在注释与设计文档里）。
  它是保险丝（防止持续截断把额度吸干），不是"接 3 次就够"的结论。
- **Q：`max_tokens` 与"模型主动停"怎么区分？** 端点枚举先映射到产品级字面量，
  再由循环统一决定续写还是收场 —— 消费方看不到端点差异，这一段有 16 条用例钉着。

## 7. 工具清单唯一算法：一份清单、三个消费者、隐身与故障分列

**工具清单唯一算法**：注册面经三道过滤（本轮白名单 / 权限规则整工具隐藏 / 是否有注册描述）
得出模型这一轮真正可见的工具；模型请求、`/help`、`/context` 账本三个消费者**共用同一个函数**。
「隐身」（策略不让露面：白名单外、被规则隐藏）与「故障」（插件没注册描述）**分列并各自带原因** ——
三句措辞本身就是判据，测试钉的就是它们。

**为什么这么设计**：改造前三个消费者各算各的 —— 请求里发 6 个工具、`/help` 打的是注册面、
账本压根没算工具。**同一个事实有三个版本**是这类系统的典型病症，"在列表里 ≠ 能跑"正是它。

**优势**：口径唯一；故障与设计分得开（插件坏了要 warn，策略不让露面只是 debug，
混在一起会让人以为某个插件坏了）；每个工具可追责（来源报是哪个插件给的）。

**追问**：
- **Q：`/context` 的工具那一行为什么不截断？** 账本的全部意义是**不编** —— 截断就得再编一句
  "还有 N 个没显示"，而 N 自己也是估的。`/tools` 相反：给人读的列表，截 80 字符，
  并在同一屏说明"模型拿到的是完整的"。
- **Q：怎么保证重构没改行为？** 先写探针把改造前的三份数字**量出来**，再让它们收敛到一个函数，
  逐条对比。不靠读代码猜，靠探针量 —— 这是这个项目的固定做法。

## 8. 子代理边界：面栈 + 名字链 + 深度上限，全在内核里算

**子代理边界**：用「面栈 + 名字栈」按**当前这一轮**计算子代理的工具面 —— 省略工具声明 = 继承父级
这一轮的面，给出声明 = 在该面内**求交**（只能更小，拿不回父级看不见的东西）；递归断开的方式是
`allow: []`（一个工具都不给）。深度上限（3 层）与拒绝理由（`嵌套太深了（a → b → c → d，上限 3 层）`）
一并由**内核**给出，结果用**判别式联合**表达（`{ok:false, reason}`），消费方按 `ok` 分支。
进度通知挂在 `agent.spawn` 事件上 —— 被拒的那次不出声（不产生"永远不回来的假账"），
插件直派的子代理也被照亮。

**为什么这么设计**：改造前边界由**调用方按"会话的全部"**算、画在插件里，于是嵌套一层就把父级
被扣掉的面拿了回来；深度保险丝也只装在 `Task` 那条路径上。**"边界"只要不在内核里，就总有第二条路。**
两条探针把这两件事量了出来（原始输出记在设计文档 §2.1）：外层那一轮看见 2 个工具，
内层省略声明却看见 **8 个 = 会话全部**；第三方插件直接递归抵达 **6 层 / 13 次模型请求**（上限是 3）。

**优势**：一处判定所有路径生效（换路径不再等于换规则）；结果类型能表达拒绝；
探针转成了**长期用例**（不是一次性脚本）：嵌套泄漏从内层 8 个收到**与父级相同的 2 个**，
插件直派从 6 层 13 次请求收到**第 4 层被内核拒**。

**追问**：
- **Q：`tools` 从"绝对白名单"变成"父面的子集"，这是弱化了吗？** 是**收紧**：以前一个写着
  `tools: ['Bash']` 的子代理，只要父级那一轮看不见 `Bash` 也拿得到；现在拿到空面。
  这条代价写在已知限制里（本阶段唯一一处可能让人"咦"一下的行为变化）。
- **Q：并发派子代理呢？** 诚实答：**今天不可达，而且已知会错位** —— 面栈是栈，并发 `spawn`
  会串味；工具调用现在是串行的。（面试里这条反而是加分项：知道自己系统的边界在哪儿。）
- **Q：怎么证明"所有路径"真被盖住？** 反向验证：把内核里那段深度判定删掉，两条用例一起红
  （**3 红 / 15 绿**）；把内层的父面改回会话注册面，**3 红 / 4 绿**；让 `allow` 不做交集，
  **1 红 / 6 绿**（只有那条不可替代的断言发力）。

## 9. 插件系统与分发：第三方只能拧紧，装 ≠ 启用

**插件系统与分发**：插件清单校验（`plugin.json`）+ 两处约定目录自动装载 + 准入闸门
（`plugins.deny` 只能关掉**掉进目录的**插件）+ classic 钩子桥接 6 个事件；第三方插件
**只能拧紧**：座位固定 `append`（内层）、`allow` 判定一律剥掉（那个判定连它自己那一层都出不去）、
`uses` 越界则整个插件不装；分发只做**本地 marketplace 索引**（无网络、无签名与校验和、无版本解析），
且**装 ≠ 启用** —— 安装落点不参与自动装载，启用只认用户级设置里写下的名字。

**为什么这么设计**：插件系统的核心是**信任边界**：第三方代码进来之后能不能把安全判定放松？
答案做成**结构**而不是约定。"装 ≠ 启用"堵的是一个具体攻击：一个克隆下来的仓库
不该能按名字点亮你全局装着的插件。

**优势**：信任面在装载期就能列全（能说上话的事件 + 能返回的判定）；供应链克制
（没有可信密钥体系时，做一个假的签名校验比不做更糟）；`hookify` 那套声明式规则即使被写坏，
也在 `PreToolUse` 上 fail-closed 翻成 deny 并出声（参考实现的钩子出错永远 `exit(0)`，
我们**不接受**那个方向：一个读不懂自己规则的守卫，比一个假装没事的守卫危险）。

**追问**：
- **Q：怎么防"插件在 `PreToolUse` 上返回 allow 把 deny 顶掉"？** `allow` 一律被剥掉；
  能返回的只有更严的判定。这不是"检查一下"，是**结构上到不了**。
- **Q：`uses` 校验粒度？** 只到事件级 —— 声明了 `tool.check` 的插件对每个工具都能说上话，
  细到 matcher 一级没做，这条**如实记进已知限制**。它的定位是减少误伤面，不是隔离机制。

## 10. 内建能力 mod 化：走同一条接口，可选依赖预检

**内建能力 mod 化**：权限裁决（`sec-default`）、指令文件（`agents-md`）、遥测、diff 四个内建模块
与第三方插件走**完全相同**的注册接口，只由 CLI 代挑座位；mod 独有「可选依赖」预检 ——
例如缺 `git` 就不装载、启动时出声（`内建 mod diff 没装：这台机器上没有 git。`）并降级到内置应答；
并保证同一条命令不出现两条应答者（mod 装上了，CLI 就不注册自己那条回退）。

**为什么这么设计**：内建能力最容易变成内核里的特权分支（"这是内置的，可以直接调"）。
按同一条注册路径外置之后，内建与第三方能被**同一套规则**检查，内建模块自己坏了也只是
"少一块 + 出声"，不会拖垮进程。降级必须看得见 —— 缺了东西却安静地少一块，比装不上还坏。

**优势**：降级可见；不重复应答；边界可强制（mod 只许 import `node:` 内建、`contract/**` 与自身目录，
反过来只有 CLI 层许 import mod，由 `pnpm lint` 强制）。

**追问**：
- **Q：为什么要有可选依赖预检，不能启动后报错？** 启动后才发现意味着用户已经进来了、界面已经开始了；
  预检让"这个功能今天不在"一开始就说清楚。不装它比装作装了更安全。
- **Q：内建和第三方真的同构吗？** 注册路径、事件契约、判定规则完全相同；差别只有两处，
  且都是**更受约束**的方向：CLI 代挑座位（内建可落 `prepend` / `builtin`，第三方只能 `append`）
  与可选依赖预检。

## 11. 终端渲染与输出契约：逐字节可测

**终端渲染与输出契约**：界面是逐行的纯文本流（不占整屏、可 `tee`、可滚回、可复制），
活动行与 spinner 只往 **stderr** 写；markdown 做**子集**的行内增强，认不出的语法原样保留、
代码块与行内代码**逐字节保真**；**非 TTY 下输出逐字节等于"没有这个界面"**，
关掉着色与"根本没有这个功能"逐字节相同（`NO_COLOR` / `FORCE_COLOR` / 是否 TTY 三者决定）。

**为什么这么设计**：CLI 的界面改动最容易破坏**可组合性**（管道、日志、diff）。
所以把"非 TTY 逐字节不变"当承重墙 —— 于是渲染层可以用**字节级断言**测，而不是靠人眼看。

**优势**：可组合；装饰不吞字；可测试（"关掉着色"与"功能不存在"逐字节相同这条，
让断言可以直接比字节）；转录不许比屏幕少东西（流中断时屏幕上显示过的半句会留在转录里）。

**追问**：
- **Q：为什么不做整屏 TUI / 语法高亮？** 逐行流能进管道、能被滚回、能被复制，整屏应用不能。
  这是取舍不是能力，所以如实写进已知限制。
- **Q：界面改动怎么防止悄悄破坏管道输出？** 非 TTY 输出逐字节不变的用例钉着 ——
  旋转器往 stderr 写、非 TTY 一个字节都不产出。

## 12. 工程护栏：边界由脚本守、CI 按 SHA 锁

**工程护栏**：`pnpm lint` 里两个自写校验器（合计约 460 行）强制「依赖边界」（`contract/` 零 import、
各层只许向下依赖、`.mjs` 也扫）与「CI 工作流硬化 H1–H7」（第三方 action 必须钉 40 位 commit SHA、
顶层显式最小 token 权限、禁 `pull_request_target`、checkout 不落凭据、出口白名单 `enforce`）；
零运行时依赖（`package.json` 只有 devDependencies），71 个文件 1187 条用例全绿，
CI 在 Node 20 与 22 各跑一遍。

**为什么这么设计**：架构约束写进文档靠自觉，改三个月就散了。变成脚本之后，"越界"这个动作
会在本地 `pnpm lint` 与 CI 上同时红 —— 约束的成本从"记得"变成"改不动"。

**优势**：边界可回归；供应链硬化可执行（tag 会被上游重指所以按 SHA 锁；`persist-credentials: false`
否则 token 写进 `.git/config`、后面任何一步都能拿去推东西）；不引依赖做这件事（校验器是手写的
文本扫描），并把**它看不见的东西**（动态拼的 `uses:`、YAML 锚点）写在文件头 ——
尽力而为的护栏，不假装是完备证明。

**追问**：
- **Q：为什么不用 ESLint 的 import 规则？** flat config 下 `import/no-restricted-paths` 支持不稳定，
  而这里要的只是"某目录不许 import"；手写脚本还顺便覆盖了 `tsc` 看不见的 `.mjs`（插件源码）。
- **Q：CI 里那个跑真引擎的 job 为什么默认跳过？** 它需要防火墙 runner，而**永远红的流水线等于没有流水线** ——
  由仓库变量显式打开；跑的时候验的是"非 TTY 下没人能确认 → 拒绝"这条 fail-closed。

## 13. 反向验证：把实现改坏，看断言红不红

**反向验证**：每个阶段的出口标准里预登记"改坏哪一处、哪条断言应该红"，然后**真的把实现改坏一次**
跑一遍；不红就说明那条断言是**摆设**，修的是断言本身。实测记录（P10 三条）：
把内层的父面改回会话注册面 → **3 红 / 4 绿**；把内核里那段深度判定删掉 → **3 红 / 15 绿**；
让 `allow` 不做交集 → **1 红 / 6 绿**。三条都先红在指定断言上，随后还原、复绿。

**为什么这么设计**：测试全绿有两种可能 —— 实现是对的，或者断言根本没在测东西。
区分这两者只有一个办法：主动把实现弄错，看测试有没有意见。

**优势**：断言的有效性可验证，而不是"覆盖率很高"这种间接证据；**红的形状**本身是证据
（同一件事的三个面一起红，说明它们咬在同一处）；做法在文档里留痕 ——
每个阶段的设计文档与变更记录里都有一张"改坏什么 → 实测几红几绿"的表。

**追问**：
- **Q：这不就是变异测试吗？** 同源思想，但**手工且便宜**：不铺工具链，只在阶段收口时挑几处
  承重的实现改坏。对个人项目来说关键是养成"红过一次"的习惯，而不是把变异覆盖率跑高。
- **Q：有没有过"改坏了却不红"的情况？** 有：上一轮执行计划时逮出计划本身的错 ——
  拿一个**可选字段**做变异，红不出来其实是变异选错了（那个字段没被别人消费）。
  修的是变异点，不是断言。

## 答辩通用三问

**Q：这个项目最难的地方是什么？**
A：不是调模型，是**边界**。两个真事：① 子代理的工具面原来由调用方按"会话的全部"算，
嵌套一层就从插件里漏出去 —— 修法不是打补丁，而是把"面"按**当前这一轮**在内核里算；
② 深度保险丝原来只装在 `Task` 那条路径上，第三方插件直接递归就绕过去了。
共同点：**边界只要不在内核里，就总有第二条路**。

**Q：如果重做，你会改什么？**
A：三条，都明写着：① 事件目录 41 个已声明里只有 22 个实现 —— 入口太多会让"这个事件谁应答"变糊，
我会先砍到真需要的那些；② 权限规则的前缀匹配不懂 shell 语法，要么老实标成"仅防手滑"，
要么把 token 化做到底；③ 压缩的阈值与断电器数字都是抄来的，重做时至少要有一次真实测量。

**Q：你怎么保证质量？**
A：三层：**结构**（边界由脚本强制，越界直接红）、**断言**（把实现改坏验证测试真会红）、
**文档**（出口标准、偏差、"我们定的数"全部留痕，包括做不到的和做得不漂亮的）。
最后一条尤其重要：可信度不来自宣称支持什么，而来自**把不确定的部分标成不确定**。

## 简历上不要写的东西

- 任何性能 / 吞吐 / 延迟 / 耗时下降数字 —— 项目里没有 benchmark，"并行子代理把总耗时降为最慢子任务"
  这种事**今天不成立**（子代理是同步交回结果的，并发 `spawn` 会让面栈错位）；
- 任何用户数、star 数、"生产可用" —— 单人仓库，没有线上；
- 把 `41 个事件` 写成 `41 个已实现` —— 事实是 41 声明 / 22 实现，其余用到时抛 `NotImplementedError`
  （面试里主动说这条反而加分：标出"还没做"比装作做完了可信）；
- 把"上下文压缩缩 60%+"这类复刻对象的数字搬过来 —— 我们没有这个测量。
