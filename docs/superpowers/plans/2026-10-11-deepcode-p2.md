# DeepCode P2（安全内核）实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把「每个动作按一次 `y`」的最小确认，长成一套可配置的权限系统：五层 settings 来源、`allow` / `ask` / `deny` 规则引擎（含 `Bash(git push:*)` 这类参数化匹配）、坐在 `prepend` 的 `sec-default` 守门器、deny 携带规则名、以及按权限过滤的工具可见性。

**Architecture:** 规则匹配是一个零依赖纯函数模块 `src/contract/policy.ts`；两个内建插件（`permissions` 坐 `user`、`sec-default` 坐 `prepend`）把规则挂到既有的 `tool.check` 事件上，引擎本身一行安全逻辑都不加。座位由 CLI 钉（`CreateEngineDeps.seating`），插件自述的权威一概不认 —— 这是「个人插件放宽不了组织策略」能从机制上成立的前提。托管策略由 `sec-default` **持有裁决**而不是文档里的「重放」（我们缺重放成立的两个前提，见设计 §11 偏差 1）。

**Tech Stack:** TypeScript（ESM，`strict` + `noUncheckedIndexedAccess` + `verbatimModuleSyntax`）、Node ≥ 20、pnpm、vitest 2.1.9、tsx。**零运行时依赖**，这一条不允许破。

**设计文档:** [`docs/superpowers/specs/2026-10-11-deepcode-p2-design.md`](../specs/2026-10-11-deepcode-p2-design.md)

```ts
import { describe, expect, it } from 'vitest';
import {
  LENIENCY,
  evaluate,
  fullyDeniedTools,
  isLooser,
  isSupported,
  matchesRule,
  parseRule,
  type Behavior,
  type Rule,
} from '../src/contract/policy';

const HOME = 'C:\\Users\\x';

/** 解析一条规则，断言没出错 —— 省掉每处判空的噪音。 */
function rule(text: string, decision: Behavior): Rule {
  const parsed = parseRule(text, decision, HOME);
  if ('error' in parsed) throw new Error(`规则 "${text}" 本该解析成功：${parsed.error}`);
  return parsed;
}

function call(tool: string, input: unknown) {
  return { tool, input };
}

describe('parseRule：形状', () => {
  it('工具名单独一条 = 该工具的所有调用', () => {
    expect(rule('Bash', 'allow')).toEqual({
      raw: 'Bash',
      tool: 'Bash',
      decision: 'allow',
    });
  });

  it('带括号的保留括号里的内容（deny 要按原文回报给人）', () => {
    expect(rule('Bash(git push:*)', 'deny')).toEqual({
      raw: 'Bash(git push:*)',
      tool: 'Bash',
      content: 'git push:*',
      decision: 'deny',
    });
  });

  it('raw 保留原样，content 已归一 —— 一个是给人看的，一个是拿来比的', () => {
    const parsed = rule('  Bash( git   push:* )  ', 'ask');
    expect(parsed.raw).toBe('  Bash( git   push:* )  ');
    expect(parsed.content).toBe('git push:*');
  });

  it('路径类规则里的 ~ 在解析时就展开成 home', () => {
    expect(rule('Read(~/.ssh/**)', 'deny').content).toBe('C:/Users/x/.ssh/**');
  });

  it('Bash 规则里的 ~ 不展开（那不是路径）', () => {
    expect(rule('Bash(~/x)', 'deny').content).toBe('~/x');
  });

  it.each([
    '',
    '   ',
    'Bash(',
    'Bash)',
    'Bash(git push',
    'Bash(git push))',
    'Bash()',
    '(git push)',
    '1Bash',
    'Ba-sh',
    'Bash(git (push)',
  ])('不合法的规则 %j 返回 error，不抛', (text) => {
    const parsed = parseRule(text, 'deny', HOME);
    expect(parsed).toHaveProperty('error');
    expect(typeof (parsed as { error: string }).error).toBe('string');
  });
});

describe('匹配：Bash', () => {
  it('无参数 = 所有 Bash 调用', () => {
    expect(matchesRule(rule('Bash', 'deny'), call('Bash', { command: 'rm -rf /' }))).toBe(true);
  });

  it('带参数不带 :* = 精确匹配整条命令行', () => {
    const r = rule('Bash(git status)', 'allow');
    expect(matchesRule(r, call('Bash', { command: 'git status' }))).toBe(true);
    expect(matchesRule(r, call('Bash', { command: 'git status --short' }))).toBe(false);
  });

  it(':* 是 token 边界上的前缀，不是通配符', () => {
    const r = rule('Bash(git push:*)', 'deny');
    expect(matchesRule(r, call('Bash', { command: 'git push' }))).toBe(true);
    expect(matchesRule(r, call('Bash', { command: 'git push origin main' }))).toBe(true);
    expect(matchesRule(r, call('Bash', { command: 'git push --force' }))).toBe(true);
    // 这一条是本文件最要紧的断言：若把 `:` 当普通通配符，规则会要求命令行里
    // 真有一个冒号，而 `git push origin main` 没有 —— 规则永远不命中，安静地失效。
    expect(matchesRule(r, call('Bash', { command: 'git pushup' }))).toBe(false);
    expect(matchesRule(r, call('Bash', { command: 'git pull' }))).toBe(false);
    expect(matchesRule(r, call('Bash', { command: 'git push' + String.fromCharCode(9) + 'x' }))).toBe(true);
  });

  it('两侧空白与连续空白都不影响匹配', () => {
    const r = rule('Bash(git   push:*)', 'deny');
    expect(matchesRule(r, call('Bash', { command: '  git  push  origin  main  ' }))).toBe(true);
  });

  it('command 不是字符串（模型胡来）时静默不匹配，不抛', () => {
    const r = rule('Bash(git push:*)', 'deny');
    expect(matchesRule(r, call('Bash', { command: 42 }))).toBe(false);
    expect(matchesRule(r, call('Bash', undefined))).toBe(false);
    expect(matchesRule(r, call('Bash', {}))).toBe(false);
  });

  it('Bash(:*) 与 Bash 同义', () => {
    expect(matchesRule(rule('Bash(:*)', 'deny'), call('Bash', { command: 'ls' }))).toBe(true);
  });
});

describe('匹配：路径 glob', () => {
  it('* 只跨一段', () => {
    const r = rule('Read(~/.ssh/*)', 'deny');
    expect(matchesRule(r, call('Read', { file_path: 'C:\\Users\\x\\.ssh\\id_rsa' }))).toBe(true);
    expect(matchesRule(r, call('Read', { file_path: 'C:\\Users\\x\\.ssh\\sub\\id_rsa' }))).toBe(false);
  });

  it('** 跨段，也吃零段', () => {
    const r = rule('Read(~/.ssh/**)', 'deny');
    expect(matchesRule(r, call('Read', { file_path: 'C:/Users/x/.ssh/id_rsa' }))).toBe(true);
    expect(matchesRule(r, call('Read', { file_path: 'C:\\Users\\x\\.ssh\\a\\b' }))).toBe(true);
    expect(matchesRule(r, call('Read', { file_path: 'C:/Users/x/.ssh' }))).toBe(false);
  });

  it('a/**/b 要能匹配 a/b', () => {
    const r = rule('Read(/x/**/b)', 'deny');
    expect(matchesRule(r, call('Read', { file_path: '/x/b' }))).toBe(true);
    expect(matchesRule(r, call('Read', { file_path: '/x/y/b' }))).toBe(true);
  });

  it('不匹配 ~/.sshx —— 前缀不能越界', () => {
    const r = rule('Read(~/.ssh/**)', 'deny');
    expect(matchesRule(r, call('Read', { file_path: 'C:/Users/x/.sshx/id_rsa' }))).toBe(false);
  });

  it('分隔符两侧归一：规则写反斜杠、调用给正斜杠也要命中', () => {
    const r = rule('Edit(C:\\Users\\x\\.npmrc)', 'deny');
    expect(matchesRule(r, call('Edit', { file_path: 'C:/Users/x/.npmrc' }))).toBe(true);
  });

  it('Write 与 Edit 也走路径匹配', () => {
    expect(
      matchesRule(rule('Write(**/secrets.json)', 'deny'), call('Write', { file_path: 'a/b/secrets.json' })),
    ).toBe(true);
  });

  it('相对路径不命中绝对路径的规则（有意为之，/permissions 会说明）', () => {
    expect(matchesRule(rule('Write(~/.npmrc)', 'deny'), call('Write', { file_path: '.npmrc' }))).toBe(false);
  });

  it('file_path 不是字符串时静默不匹配', () => {
    expect(matchesRule(rule('Read(~/.ssh/**)', 'deny'), call('Read', {}))).toBe(false);
  });

  it('工具名不同就不匹配', () => {
    expect(
      matchesRule(rule('Read(~/.npmrc)', 'deny'), call('Write', { file_path: 'C:/Users/x/.npmrc' })),
    ).toBe(false);
  });
});

describe('isSupported：其它工具带括号 = 永不命中', () => {
  it('Bash 与三个路径工具支持参数', () => {
    expect(isSupported(rule('Bash(git push:*)', 'deny'))).toBe(true);
    expect(isSupported(rule('Read(~/.ssh/**)', 'deny'))).toBe(true);
    expect(isSupported(rule('Write(~/.npmrc)', 'deny'))).toBe(true);
    expect(isSupported(rule('Edit(~/.npmrc)', 'deny'))).toBe(true);
  });

  it('不带括号的永远支持', () => {
    expect(isSupported(rule('WebSearch', 'deny'))).toBe(true);
  });

  it('其它工具带括号：不支持，加载时要吼一次', () => {
    expect(isSupported(rule('Grep(rm -rf)', 'deny'))).toBe(false);
    expect(isSupported(rule('Glob(*.ts)', 'deny'))).toBe(false);
  });

  it('不支持的规则也确实永不命中（不是"支持但没实现"）', () => {
    expect(matchesRule(rule('Grep(rm -rf)', 'deny'), call('Grep', { pattern: 'rm -rf' }))).toBe(false);
  });
});

describe('evaluate：固定的 deny > ask > allow', () => {
  const rules = [
    rule('Bash', 'allow'),
    rule('Bash(git push:*)', 'ask'),
    rule('Bash(git push --force:*)', 'deny'),
  ];

  it('三条都命中时 deny 赢', () => {
    expect(evaluate(rules, call('Bash', { command: 'git push --force origin main' }))).toEqual({
      decision: 'deny',
      rule: 'Bash(git push --force:*)',
    });
  });

  it('把数组倒过来，结果一模一样 —— 重排配置不该换行为', () => {
    expect(evaluate([...rules].reverse(), call('Bash', { command: 'git push --force origin main' }))).toEqual({
      decision: 'deny',
      rule: 'Bash(git push --force:*)',
    });
  });

  it('deny 不命中时 ask 赢', () => {
    expect(evaluate(rules, call('Bash', { command: 'git push origin main' }))).toEqual({
      decision: 'ask',
      rule: 'Bash(git push:*)',
    });
  });

  it('只有 allow 命中时才 allow', () => {
    expect(evaluate(rules, call('Bash', { command: 'git status' }))).toEqual({
      decision: 'allow',
      rule: 'Bash',
    });
  });

  it('一条都不命中 = undefined（原样交给下游）', () => {
    expect(evaluate(rules, call('Read', { file_path: 'x' }))).toBeUndefined();
    expect(evaluate([], call('Bash', { command: 'ls' }))).toBeUndefined();

  it('同一档里按数组顺序取第一条，规则名要能对上号', () => {
    const two = [rule('Bash(git:*)', 'deny'), rule('Bash(git push:*)', 'deny')];
    expect(evaluate(two, call('Bash', { command: 'git push' }))?.rule).toBe('Bash(git:*)');

    expect(LENIENCY).toEqual({ deny: 0, ask: 1, allow: 2 });

  it('方向', () => {

    expect(isLooser('deny', 'deny')).toBe(false);
    expect(isLooser('deny', 'allow')).toBe(false);
```

```ts
/**
 * 权限规则的解析、匹配与优先级。
 *
 * 放在 `contract/` 是因为依赖边界规定 `builtins: ['contract']`，而 `permissions`
 * 与 `sec-default` 两个内建插件都要用它。`contract/tier.ts` 已经带了 `tierIndex`
 * 这种纯逻辑，是同一条先例：**零依赖、零 IO、纯函数**。
 *
 * 这个文件里没有任何一处知道"settings 从哪来"、"谁有权改规则" —— 那是 cli/settings.ts
 * 与两个插件的事。
 */

export type Behavior = 'allow' | 'ask' | 'deny';

export type Rule = {
  /** 规则原文，原样保留。deny 要按它"持有"，也按它回报给人。 */
  readonly raw: string;
  readonly tool: string;
  /**
   * 已归一化（空白折叠、分隔符统一、`~` 已展开）。`undefined` = 该工具的所有调用。
   * 归一在**解析时**做一次，匹配时只归一调用侧 —— 规则是启动期定下的，不该每次重算。
   */
  readonly content?: string;
  readonly decision: Behavior;
};

export type ParsedRule = Rule | { readonly error: string };

/** 一次工具调用。与 `tool.check` 的事件参数同形。 */
export type Call = { readonly tool: string; readonly input: unknown };

export type Verdict = { readonly decision: Behavior; readonly rule: string };

/** deny 最严，allow 最松。数字只用于比较，"谁赢"仍由 `evaluate` 的固定优先级决定。 */
export const LENIENCY: Record<Behavior, number> = { deny: 0, ask: 1, allow: 2 };

/** a 是否比 b 宽松。相等不算。 */
export function isLooser(a: Behavior, b: Behavior): boolean {
  return LENIENCY[a] > LENIENCY[b];
}

/**
 * 取 `file_path` 的工具。带参规则按路径 glob 匹配的就这三个。
 *
 * `Glob` / `Grep` 不在里面：它们的参数是 `pattern`（一个正则或文件名式），不是路径 ——
 * 拿路径 glob 去比一个正则，只会得到一条永远不命中的规则。
 */
const PATH_TOOLS: ReadonlySet<string> = new Set(['Read', 'Write', 'Edit']);

/** 工具名：字母开头，之后字母 / 数字 / 下划线。 */
const TOOL_NAME_RE = /^[A-Za-z][A-Za-z0-9_]*$/;

/** 连续空白折成单空格、去首尾。规则侧与调用侧都要做，`git  push` 才等于 `git push`。 */
function squeeze(text: string): string {
  return text.trim().replace(/\s+/g, ' ');
}

/** 反斜杠统一成正斜杠，免得同一个路径因为写法不同而匹配不上。 */
function slashes(text: string): string {
  return text.replace(/\\/g, '/');
}

/**
 * `~` → home，只在开头且后面跟着分隔符（或就是它自己）。
 *
 * 规则侧的 `~` 由调用方在解析时展开；**调用侧不展开** —— 模型给 `Read` 传 `~/.ssh/id_rsa`
 * 本来就该由 fs 名词去管，绕到这里来只会让匹配和真实行为对不上。
 */
function expandHome(text: string, home: string): string {
  if (text === '~') return home;
  if (text.startsWith('~/') || text.startsWith('~\\')) return home + text.slice(1);
  return text;
}

/**
 * 解析一条规则。五类坏输入返回 `{ error }`，**不抛** —— 调用方要把 error 连同
 * 原文报到人面前（见 cli/settings.ts），抛出去就没原文了。
 */
export function parseRule(text: string, decision: Behavior, home: string): ParsedRule {
  const raw = text;
  const trimmed = text.trim();
  if (trimmed === '') return { error: '规则是空的' };

  const open = trimmed.indexOf('(');
  if (open === -1) {
    if (trimmed.includes(')')) return { error: '括号不配对' };
    if (!TOOL_NAME_RE.test(trimmed)) return { error: `工具名 "${trimmed}" 不合法` };
    return { raw, tool: trimmed, decision };
  }

  if (!trimmed.endsWith(')')) return { error: '括号不配对' };

  const tool = trimmed.slice(0, open).trim();
  const content = trimmed.slice(open + 1, -1).trim();

  if (!TOOL_NAME_RE.test(tool)) return { error: `工具名 "${tool}" 不合法` };
  if (content === '') return { error: '括号里是空的' };
  if (content.includes('(') || content.includes(')')) return { error: '括号不配对' };

  const normalized =
    tool === 'Bash'
      ? squeeze(content)
      : PATH_TOOLS.has(tool)
        ? slashes(squeeze(expandHome(content, home))).replace(/\/+/g, '/')
        : content;

  return { raw, tool, content: normalized, decision };
}

/**
 * 这条规则有没有可能真的命中。
 *
 * 只有 `Bash` 与三个路径工具的带参形式实现了参数匹配，其它工具带括号是我们**不支持**
 * 的写法。它必须吼一次（§7），否则写的人会以为自己在防一件其实没防的事。
 */
export function isSupported(rule: Rule): boolean {
  if (rule.content === undefined) return true;
  return rule.tool === 'Bash' || PATH_TOOLS.has(rule.tool);
}

export function matchesRule(rule: Rule, call: Call): boolean {
  if (rule.tool !== call.tool) return false;
  if (rule.content === undefined) return true;

  if (rule.tool === 'Bash') return matchesBash(rule.content, call.input);
  if (PATH_TOOLS.has(rule.tool)) return matchesPath(rule.content, call.input);
  // 不支持的带参规则：永不命中。加载时已经警告过一次，这里安静。
  return false;
}

/** 从工具入参里取一个字符串字段。取不到（缺、类型不对）就当不匹配，不抛。 */
function readString(input: unknown, key: string): string | undefined {
  if (typeof input !== 'object' || input === null) return undefined;
  const value = (input as Record<string, unknown>)[key];
  return typeof value === 'string' ? value : undefined;
}

/**
 * `cmd` 精确；`cmd:*` 是**空白 token 边界上的前缀**。
 *
 * `:*` 必须按 token 边界解释，不能当普通通配符：当通配符的话，`Bash(git push:*)`
 * 会要求命令行里真有一个冒号，而 `git push origin main` 没有 —— 规则永远不命中，
 * 安静地失效。（`content` 已在 `parseRule` 里归一过了。）
 */
function matchesBash(content: string, input: unknown): boolean {
  const command = readString(input, 'command');
  if (command === undefined) return false;
  const normalized = squeeze(command);

  if (content.endsWith(':*')) {
    const prefix = content.slice(0, -2).trim();
    if (prefix === '') return true; // `Bash(:*)` 与 `Bash` 同义
    return normalized === prefix || normalized.startsWith(`${prefix} `);
  }
  return normalized === content;
}

const GLOB_SPECIAL = /[.+^${}()|[\]\\?]/;

/** `*` 单段、`**` 跨段。输入是已归一（正斜杠）的绝对路径式模式。 */
function globToRegExp(pattern: string): RegExp {
  let out = '';
  for (let i = 0; i < pattern.length; i++) {
    const ch = pattern[i]!;
    if (ch !== '*') {
      out += GLOB_SPECIAL.test(ch) ? `\\${ch}` : ch;
      continue;
    }
    if (pattern[i + 1] === '*') {
      // `**/` 也吃零段：`a/**/b` 要能匹配 `a/b`。
      if (pattern[i + 2] === '/') {
        out += '(?:.*/)?';
        i += 2;
      } else {
        out += '.*';
        i += 1;
      }
      continue;
    }
    out += '[^/]*';
  }
  return new RegExp(`^${out}$`);
}

function matchesPath(pattern: string, input: unknown): boolean {
  const filePath = readString(input, 'file_path');
  if (filePath === undefined) return false;
  return globToRegExp(pattern).test(slashes(filePath));
}

/**
 * 扫全部规则，各按行为分桶；**桶顺序固定 `deny → ask → allow`**，第一个非空的桶里
 * 取第一条命中的，返回 `{ decision, rule: 该条原文 }`。未命中返回 `undefined`。
 *
 * 为什么是固定优先级而不是"先到先得"：更严的永远赢，与全局 fail-closed 同方向，
 * 且结果与数组顺序无关 —— 重排一下配置文件不会换行为。
 *
 * 注意这与 `isLooser` **无关**：那个是 `sec-default` 衡量"下游相对策略放宽了多少"
 * 的尺子，不是规则之间的优先级规则。两者容易混为一谈。
 */
export function evaluate(rules: readonly Rule[], call: Call): Verdict | undefined {
  for (const decision of ['deny', 'ask', 'allow'] as const) {
    for (const rule of rules) {
      if (rule.decision === decision && matchesRule(rule, call)) {
        return { decision, rule: rule.raw };
      }
    }
  }
  return undefined;
}

/**
 * 被**整工具** deny 的工具名（去重，按首次出现序）。
 *
 * 只有不带括号的 deny 算。参数化 deny（`Bash(git push:*)`）绝不隐藏整个工具 ——
 * 为了拦一条命令就把整个 Bash 从模型眼前藏掉是灾难。
 */
export function fullyDeniedTools(rules: readonly Rule[]): string[] {
  const names = new Set<string>();
  for (const rule of rules) {
    if (rule.decision === 'deny' && rule.content === undefined) names.add(rule.tool);
  }
  return [...names];
}
```

```ts
import { existsSync } from 'node:fs';
import { readFile } from 'node:fs/promises';
import { join, resolve } from 'node:path';
import { isSupported, parseRule, type Behavior, type Rule } from '../contract/policy';

/**
 * 权限设置的五个来源，低 → 高。数组顺序就是 `/permissions` 的输出顺序。
 *
 * 这一层**刻意没有环境变量来源**：`config.json` 有，是因为"别把 key 写进文件"
 * 是真需求；权限不一样 —— 一个环境变量就能改掉权限，等于在规则引擎上开了个后门。
 * 托管策略必须来自文件。见设计 §4.4。
 */
export const SETTINGS_SOURCES = ['user', 'project', 'local', 'flag', 'policy'] as const;
export type SettingsSource = (typeof SETTINGS_SOURCES)[number];

export type SourceInfo = {
  readonly source: SettingsSource;
  /** 这一层实际读的路径。`flag` 没给 `--settings=` 时是 undefined。 */
  readonly path: string | undefined;
  readonly state: 'missing' | 'ok' | 'broken';
  /** `state === 'broken'` 时的原因，直接给人看。 */
  readonly error?: string;
  readonly counts: { allow: number; ask: number; deny: number };
  /** 逐条规则的问题（含原文与原因）。有问题不等于整个文件坏掉。 */
  readonly problems: readonly string[];
  /** 这一层真正收下的规则。/permissions 要用它标出每条规则来自哪一层。 */
  readonly rules: readonly Rule[];
};

export type ResolvedPolicy = {
  readonly sources: readonly SourceInfo[];
  /** **只**来自 policy 源。给 sec-default。 */
  readonly policyRules: readonly Rule[];
  /** 其余四源的并集。给 permissions。 */
  readonly personalRules: readonly Rule[];
};

/**
 * 读一个文本文件。两种失败必须分得开：
 * - 返回 `undefined` = 文件**不存在**（正常，绝大多数机器没有托管文件）
 * - **抛** = 文件存在但读不了（权限、是个目录、编码）—— 这一条是设计里唯一的 fail-open，要吼
 */
export type TextReader = (path: string) => Promise<string | undefined>;

export const defaultTextReader: TextReader = async (path) => {
  if (!existsSync(path)) return undefined;
  // 目录也会过 existsSync，于是 readFile 抛 EISDIR —— 正好落进"存在但读不了"。
  return readFile(path, 'utf8');
};

/** 托管策略文件的位置。`env` 与 `platform` 可注入，测试才不必碰系统目录。 */
export function defaultManagedPath(
  env: Record<string, string | undefined> = process.env,
  platform: string = process.platform,
): string {
  if (platform === 'win32') {
    const base = env.ProgramFiles ?? env.PROGRAMFILES ?? 'C:\\Program Files';
    return join(base, 'DeepCode', 'managed-settings.json');
  }
  return '/etc/deepcode/managed-settings.json';
}

export type ResolvePolicyDeps = {
  readonly home: string;
  readonly root: string;
  /** `--settings=<路径>` 的取值。相对路径按 cwd 解析，与 `--resume=<id>` 同一个规矩。 */
  readonly settingsPath?: string;
  /** 覆盖托管文件位置（`DEEPCODE_MANAGED_SETTINGS` 从这进）。 */
  readonly managedPath?: string;
  readonly warn?: (line: string) => void;
  readonly readText?: TextReader;
};

const EMPTY_COUNTS = { allow: 0, ask: 0, deny: 0 } as const;

function label(source: SettingsSource): string {
  return source === 'policy' ? '⚠️ 托管策略' : `[权限] ${source} 设置`;
}

type Layer = { readonly source: SettingsSource; readonly path: string | undefined };

export async function resolvePolicy(deps: ResolvePolicyDeps): Promise<ResolvedPolicy> {
  const warn = deps.warn ?? (() => {});
  const readText = deps.readText ?? defaultTextReader;

  const layers: readonly Layer[] = [
    { source: 'user', path: join(deps.home, '.deepcode', 'settings.json') },
    { source: 'project', path: join(deps.root, '.deepcode', 'settings.json') },
    { source: 'local', path: join(deps.root, '.deepcode', 'settings.local.json') },
    {
      source: 'flag',
      path: deps.settingsPath === undefined ? undefined : resolve(deps.settingsPath),
    },
    { source: 'policy', path: deps.managedPath ?? defaultManagedPath() },
  ];

  const sources: SourceInfo[] = [];
  const bySource = new Map<SettingsSource, readonly Rule[]>();

  for (const layer of layers) {
    const read = await readLayer(layer, deps.home, warn, readText);
    sources.push(read.info);
    bySource.set(layer.source, read.rules);
  }

  return {
    sources,
    // policy 源 vs. 其余全部 —— 在固定优先级下这是唯一承重的划分（设计 §4.3）。
    policyRules: bySource.get('policy') ?? [],
    personalRules: SETTINGS_SOURCES.filter((s) => s !== 'policy').flatMap((s) => bySource.get(s) ?? []),
  };
}

type LayerRead = { readonly info: SourceInfo; readonly rules: readonly Rule[] };

async function readLayer(
  layer: Layer,
  home: string,
  warn: (line: string) => void,
  readText: TextReader,
): Promise<LayerRead> {
  const where = layer.path;

  if (where === undefined) {
    return { info: base(layer, 'missing', undefined, [], []), rules: [] };
  }

  const broken = (error: string): LayerRead => {
    warn(`${label(layer.source)} ${where} ${error} —— 这一层按空处理。`);
    return { info: base(layer, 'broken', error, [], []), rules: [] };
  };

  let text: string | undefined;
  try {
    text = await readText(where);
  } catch (error) {
    return broken(`读不了（${error instanceof Error ? error.message : String(error)}）`);
  }
  // 不存在 = 静默为空。绝大多数机器没有托管文件，为此吼一声只会训练人无视警告。
  if (text === undefined) return { info: base(layer, 'missing', undefined, [], []), rules: [] };

  let data: unknown;
  try {
    data = JSON.parse(text);
  } catch (error) {
    return broken(`JSON 语法错（${error instanceof Error ? error.message : String(error)}）`);
  }
  if (typeof data !== 'object' || data === null || Array.isArray(data)) {
    return broken('顶层不是一个对象');
  }

  const record = data as Record<string, unknown>;

  const unknown = Object.keys(record).filter((key) => key !== 'permissions');
  if (unknown.length > 0) {
    // 未知键只警告、不致命：将来加顶层键（hooks、env）时，旧版本读新文件不该整份失效。
    warn(`${label(layer.source)} ${where} 里有不认识的顶层键：${unknown.join('、')}（已忽略）。`);
  }

  const raw = record.permissions;
  if (raw === undefined) return { info: base(layer, 'ok', undefined, [], []), rules: [] };
  if (typeof raw !== 'object' || raw === null || Array.isArray(raw)) {
    return broken('permissions 不是一个对象');
  }

  const perms = raw as Record<string, unknown>;
  const counts = { allow: 0, ask: 0, deny: 0 };
  const problems: string[] = [];
  const rules: Rule[] = [];

  for (const key of ['allow', 'ask', 'deny'] as const) {
    const value = perms[key];
    if (value === undefined) continue;

    if (!Array.isArray(value)) return broken(`permissions.${key} 不是数组`);

    const bad = value.findIndex((item) => typeof item !== 'string');
    // 整份文件作废，而不是只丢这一条：类型不对说明写的人以为它生效了。
    // 只丢一半的话，他会看到"文件被读进去了"，然后以为没报错的那几行在管事。
    if (bad !== -1) return broken(`permissions.${key}[${bad}] 不是字符串`);

    for (const text_ of value as string[]) {
      const parsed = parseRule(text_, key, home);
      if ('error' in parsed) {
        // 唯一一处"坏了就等于没写"：方向是**不收紧**，所以必须吼，不能安静。
        problems.push(`${key}: ${JSON.stringify(text_)} —— ${parsed.error}`);
        continue;
      }
      if (!isSupported(parsed)) {
        problems.push(
          `${key}: ${JSON.stringify(text_)} —— ${parsed.tool} 的参数匹配不支持，这条永远不会命中`,
        );
        continue;
      }
      rules.push(parsed);
      counts[key] += 1;
    }
  }

  for (const problem of problems) {
    warn(`${label(layer.source)} ${where} 这条不生效 —— ${problem}`);
  }

  return { info: base(layer, 'ok', undefined, problems, rules), rules };
}

function base(
  layer: Layer,
  state: SourceInfo['state'],
  error: string | undefined,
  problems: readonly string[],
  rules: readonly Rule[],
): SourceInfo {
  const counts: Record<Behavior, number> = { ...EMPTY_COUNTS };
  for (const rule of rules) counts[rule.decision] += 1;
  return { source: layer.source, path: layer.path, state, ...(error === undefined ? {} : { error }), counts, problems, rules };
}
```

```ts
/**
 * 把一个插件按指定 tier 装进 harness。
 *
 * harness 的 `on` 要求 tier 显式给（这是它能测任意座位的前提），而插件拿到的是
 *「绑好身份」的 on —— 这里做一次适配。座位仍由调用方钉，与生产里 `cliPlugins`
 * 返回的那张 seating 表同一个道理：插件自己说了不算。
 */
export function seat(h: ReturnType<typeof createHarness>, plugin: Plugin, tier: Tier): void {
  const on = ((pattern: string, second: unknown, third?: unknown) => {
    const hook = (third ?? second) as EventHook;
    const matcher = third as Record<string, unknown> | undefined;
    if (matcher !== undefined) h.on(tier, plugin.name, pattern, matcher, hook);
    else h.on(tier, plugin.name, pattern, hook);
  }) as On;
  plugin.register(on);
}

/**
 * 会记下每次请求里模型看到的工具清单的 provider。
 *
 *「按权限过滤工具可见性」只能从这里验 —— 那是模型眼里的东西，别处看不见。
 */
export function recordingProvider(): { provider: ModelProvider; lastTools(): string[] } {
  let tools: string[] = [];
  return {
    lastTools: () => tools,
    provider: {
      name: 'recording',
      async *stream(req: StreamRequest) {
        tools = req.tools.map((t) => t.name);
        yield { type: 'done', stopReason: 'end_turn' } as const;
      },
    },
  };
}
```

```ts
import { evaluate, fullyDeniedTools, type Behavior, type Rule } from '../contract/policy';
import type { Plugin } from '../contract/plugin';

export type PermissionsDeps = {
  /** 个人/项目/local/flag 四源的并集。**不含** policy —— 那是 sec-default 的事。 */
  readonly rules: readonly Rule[];
};

/**
 * 规则插件。坐 `user` 层，挂在 `confirm` 外面，只是把规则叠在它的答案之上。
 *
 * 它没有自己的"知识"：没命中规则就原样下沉，于是没配规则时行为与 P1 逐条一致。
 * 这是出口标准"fail-closed 未退化"的落点。
 */
export function createPermissionsPlugin(deps: PermissionsDeps): Plugin {
  return {
    name: 'permissions',
    uses: ['tool.check', 'tool.describe'],

    register(on) {
      on('tool.check', async (_$, e, next) => {
        const hit = evaluate(deps.rules, { tool: e.tool, input: e.input });
        if (hit === undefined) return next(e);

        const downstream = await next(e);

        // 下游是 deny 时规则不许放宽 —— allow 规则的效力上限是"把 ask 变成 allow"。
        // 少了这一条，一条宽泛的 `allow: ["Bash"]` 就能把 confirm 的未知工具拒绝
        // 也一并抹掉，而那条拒绝是 P1 的 fail-closed。
        const decision: Behavior = downstream.decision === 'deny' ? 'deny' : hit.decision;
        // rule 一律填规则原文。这是出口标准"deny 携带规则名"的地基。
        return { decision, rule: hit.rule };
      });

      // 只有整工具 deny（不带括号）才隐藏工具。
      // 参数化 deny 绝不隐藏整个工具 —— 为了拦一条命令就把整个 Bash 从模型眼前
      // 藏掉是灾难，不是安全。
      for (const tool of fullyDeniedTools(deps.rules)) {
        on('tool.describe', { tool }, (() => ({ hidden: true })) as never);
      }
    },
  };
}
```

> `as never` 是为了绕过 `On` 重载对返回类型的推断。若 typecheck 报错，改成 `() => ({ hidden: true } as const)` 并给回调标上 `EventHookFor<'tool.describe'>`；以 `pnpm typecheck` 的实际输出为准。

```ts
import { evaluate, fullyDeniedTools, isLooser, type Rule } from '../contract/policy';
import type { Plugin } from '../contract/plugin';

/** 检查没跑完时用的规则名。它会被原样报给用户，所以写成一句话而不是一个代号。 */
export const UNCHECKED_DENY = 'sec-default: 检查未完成，按拒绝处理';

export type SecDefaultDeps = {
  /** **只**来自 policy 源。个人/项目/local/flag 里的同名规则永远不参与。 */
  readonly rules: readonly Rule[];
};

/**
 * 守门器。坐 `prepend` 首位，目的只有一个：维护组织既有控制面不被个人插件放宽。
 *
 * 它不制定任何策略 —— 没配托管文件时它什么都不做，一切照常由 confirm 决定。
 *
 * 为什么是"持有"而不是架构文档里的"重放"：重放成立需要两个前提（引擎按调用者
 * 作用域重算裁决、`settings.read` 本身是可被 hook 的事件），我们一个都没有 ——
 * 设置是启动期解析好的不可变数组。这种情况下重放必然得到与第一遍相同的答案，
 * 是装样子。持有直接把策略裁决拿在手里，比重放更强：少一段可能被插手的推导路。
 */
export function createSecDefaultPlugin(deps: SecDefaultDeps): Plugin {
  return {
    name: 'sec-default',
    uses: ['tool.check', 'tool.describe', 'ui'],

    register(on) {
      on('tool.check', async ($, e, next) => {
        try {
          // 先把链跑完：策略没意见时，答案完全由下游决定，行为与 P1 逐条一致。
          const below = await next(e);
          const policy = evaluate(deps.rules, { tool: e.tool, input: e.input });

          // 三种不插手的情形，都在这一行里：
          // - 策略没提到这次调用（policy === undefined）
          // - 策略不比下游更严（更松或相同）—— 包括"策略是 allow、下层是 ask"：
          //   守门器的职责是防放宽，不是替个人取消他自己多要的那次询问。
          //   若让策略在这里也赢，一条 `allow: ["Bash"]` 就成了自动放行开关，
          //   与"谁加自动放行开关谁就是在开倒车"直接冲突。
          if (policy === undefined || policy.decision === 'allow') return below;
          if (!isLooser(below.decision, policy.decision)) return below;

          // 下游确实放宽了。持有裁决：直接拿策略的规则原文作答。
          $.ui.log(
            `[安全] 一条更宽松的判定被拦下：策略里 ${policy.rule} 要求 ${policy.decision}，` +
              `实际得到 ${below.decision}。以托管策略为准。`,
          );
          return { decision: policy.decision, rule: policy.rule };
        } catch (error) {
          // ⚠️ 这一条不是装饰。dispatch 的故障隔离会把抛错的 hook 跳过并继续跑下层 ——
          // 守门器一旦自己炸了，它的保护会**无声消失**，而 confirm 会照常给出 ask。
          // 那是一条真实的 fail-open 通道：守门器必须自己兜底成 deny，不能指望引擎替它兜。
          $.ui.log(`[安全] ${UNCHECKED_DENY}（${error instanceof Error ? error.message : String(error)}）`);
          return { decision: 'deny', rule: UNCHECKED_DENY };
        }
      });

      // 策略里的整工具 deny，用与 permissions 相同的一套机制隐藏。
      // 坐 prepend，所以策略的隐藏先于个人的隐藏生效。
      for (const tool of fullyDeniedTools(deps.rules)) {
        on('tool.describe', { tool }, (() => ({ hidden: true })) as never);
      }
    },
  };
}
```

```ts
import type { Palette } from './ansi';
import type { Plugin } from '../contract/plugin';
import { fullyDeniedTools, type Rule } from '../contract/policy';
import type { ResolvedPolicy, SettingsSource } from './settings';

/**
 * `/permissions`：把当前生效的权限设置摊开给人看。
 *
 * 住 `cli/`（与 `createSessionCommands` 同理）：它要着色、要一份设置快照，
 * 不是内建工具层的事。
 *
 * 它存在的理由不只是方便：整套设计里有**两处**失败方向是"不收紧"（单条规则
 * 解析失败、托管文件坏掉），兜底全靠"吼出来 + 这里看得到"。审计输出是那两处
 * 唯一的补救手段，不是附加功能。
 */
export type PermissionsCommandDeps = {
  readonly policy: ResolvedPolicy;
  readonly palette: Palette;
};

export function createPermissionsCommand(deps: PermissionsCommandDeps): Plugin {
  return {
    name: 'permissions-command',
    uses: ['command.run', 'ui'],

    register(on) {
      on('command.run', { name: 'permissions' }, ($) => {
        $.ui.log(renderPermissions(deps.policy, deps.palette));
        return { handled: true };
      });
    },
  };
}

const NAME_WIDTH = 8;

function countsOf(rules: readonly Rule[]): string {
  const allow = rules.filter((r) => r.decision === 'allow').length;
  const ask = rules.filter((r) => r.decision === 'ask').length;
  const deny = rules.filter((r) => r.decision === 'deny').length;
  return `${rules.length} 条（allow ${allow} / ask ${ask} / deny ${deny}）`;
}

export function renderPermissions(policy: ResolvedPolicy, palette: Palette): string {
  const lines: string[] = [];

  lines.push('权限来源（低 → 高）');
  for (const info of policy.sources) {
    const name = info.source.padEnd(NAME_WIDTH);
    const where = info.path ?? '--settings 未给';
    if (info.state === 'broken') {
      lines.push(`  ${name} ${where}`);
      lines.push(`  ${' '.repeat(NAME_WIDTH)} ${palette.red(`坏掉了：${info.error ?? '读不了'}`)}`);
      continue;
    }
    const mark = info.source === 'policy' ? '  ← 托管' : '';
    const state = info.state === 'missing' ? '不存在' : countsOf(info.rules);
    lines.push(`  ${name} ${where}  ${state}${mark}`);
  }

  // 生效规则按 来源顺序（低 → 高）逐条列出，每条带上是哪一层给的 ——
  // 层序本身不参与裁决，它只在这里有用。
  lines.push('');
  lines.push('生效规则');
  const effective = policy.sources.flatMap((info) => info.rules.map((rule) => ({ rule, from: info.source })));
  if (effective.length === 0) {
    lines.push('  （一条都没有：所有动作都按最小确认走）');
  }
  for (const { rule, from } of effective) {
    const behavior = rule.decision.padEnd(6);
    const colored = rule.decision === 'deny' ? palette.red(behavior) : behavior;
    lines.push(`  ${colored} ${rule.raw.padEnd(34)} ${sourceLabel(from)}`);
  }

  const hidden = [
    ...fullyDeniedTools(policy.policyRules),
    ...fullyDeniedTools(policy.personalRules),
  ];
  if (hidden.length > 0) {
    lines.push('');
    lines.push('隐藏的工具（整工具 deny，模型看不见它们）');
    for (const tool of hidden) lines.push(`  ${tool}`);
  }

  const problems = policy.sources.flatMap((info) =>
    info.problems.map((problem) => ({ problem, from: info.source })),
  );
  if (problems.length > 0) {
    lines.push('');
    lines.push(palette.red(`有问题、未生效的规则（${problems.length} 条）`));
    for (const { problem, from } of problems) {
      lines.push(`  ${sourceLabel(from)}  ${problem}`);
    }
  }

  lines.push('');
  lines.push('规则里的路径按绝对路径匹配（~ 会展开成主目录）；相对路径不会命中。');
  lines.push('更严的永远赢：deny > ask > allow，与规则写在哪一层、写成什么顺序无关。');

  return lines.join('\n');
}

function sourceLabel(source: SettingsSource): string {
  return `[${source}]`;
}
```

```ts
  readonly seating: Record<string, Tier>;

 *
 * 抽成函数只为一件事：让测试钉住"模型文本的出口确实在这份清单里"。
 * 原先这张表直接写在 main() 里，而 main() 一 import 就会跑起来，

 *
 * P2 之后它多了一件事：座位不再由引擎默认（`builtin`），而是这里显式钉。
 */
export function cliPlugins(deps: CliPluginDeps): CliPluginBundle {
  return {
    // ⚠️ 顺序是契约，不是随手排的：
    // 1. 座位比顺序更重要：prepend 的 sec-default 与 user 的 permissions 天然在外层，
    //    无论它们在数组里排第几。数组顺序只在**同 tier 内**有效。
    // 2. session-changes 必须排在 coreTools **之前**：同 tier 内先装载者在外层，
    //    而它要在 tool-write 自己的 hook 跑之前抢到文件的**原样**。晚一步，
    //    next 回来时文件已经写完了，before 就成了 after 的副本，/diff 永远空白。

    plugins: [
      // 守门器：只持有托管策略，读个人规则一个字都不读。
      createSecDefaultPlugin({ rules: deps.policy.policyRules }),
      // 个人规则：policy 之外的四个来源。
      createPermissionsPlugin({ rules: deps.policy.personalRules }),
      createChangesPlugin(deps.changes),
      ...coreTools,
      confirmPlugin,
      commandsPlugin,
      streamPlugin(deps.render),
      // /diff、/clear 要碰渲染会话语状态，所以住在 cli/ 而不是 builtins/（见 cli/commands.ts）。
      createSessionCommands({
        changes: deps.changes,

        root: deps.root,
        palette: deps.palette,
      }),
      // /permissions 同理。
      createPermissionsCommand({ policy: deps.policy, palette: deps.palette }),
    ],
    seating: {
      'sec-default': 'prepend',
      permissions: 'user',
    },
  };
}
```

在「配置」一节之后、「会话落盘」之前插入：

````markdown
## 权限

`config.json` 管连接，权限是另一套：`.deepcode/settings.json`。

```json
{
  "permissions": {
    "allow": ["Read"],
    "ask":   ["Bash"],
    "deny":  ["Bash(git push:*)", "WebSearch"]
  }
}
```

三组数组都可省略。五个来源从低到高：

| 来源 | 路径 |
|---|---|
| `user` | `~/.deepcode/settings.json` |
| `project` | `<工作目录>/.deepcode/settings.json` |
| `local` | `<工作目录>/.deepcode/settings.local.json` |
| `flag` | `deepcode --settings=<路径>` |
| `policy` | 托管文件，见下 |

**`policy` 这一层刻意没有环境变量来源。** `config.json` 有（"别把 key 写进文件"是真需求），
权限不一样 —— 一个环境变量就能改掉权限，等于在规则引擎上开了个后门。托管策略必须来自文件：

- Windows：`%ProgramFiles%\DeepCode\managed-settings.json`
- 其它平台：`/etc/deepcode/managed-settings.json`

> 托管文件存在但**读不了**时，这一层按空处理，只打一行醒目的警告。这是本设计里唯一一条
> 真正的 fail-open，且无法消除：策略文件按定义是可选的，不存在时静默是正确行为；
> 存在却读不了时，"拒绝启动"对一个个人 CLI 是过度反应。**看到那行警告就是没有守护。**

### 规则怎么写

| 写法 | 含义 |
|---|---|
| `Bash` | 该工具的**所有**调用 |
| `Bash(git push)` | 命令行恰好等于 `git push` |
| `Bash(git push:*)` | 命令行以 `git push` 开头，按空白 token 边界 —— `git push origin main` ✓，`git pushup` ✗ |
| `Read(~/.ssh/**)` | `file_path` 按 glob 匹配：`*` 单段、`**` 跨段 |
| `Edit(...)` / `Write(...)` | 同 `Read`，都匹配 `file_path` |
| 其它工具带括号 | **不支持**：不命中，且启动时警告一次 |

`:` 是 token 边界，不是通配符 —— 当通配符的话 `Bash(git push:*)` 会要求命令里真有个冒号，
`git push origin main` 没有，规则永远不命中，安静地失效。

路径规则按**绝对路径**匹配（`~` 会展开成主目录）；相对路径不会命中。大小写按平台原样比较，
不替文件系统做归一 —— 猜错的症状是一条防御规则悄悄不命中。

### 谁赢

**更严的永远赢：`deny` > `ask` > `allow`。** 与规则写在哪一层、在同一数组里排第几都无关 ——
重排一下配置文件不会换行为。托管策略因此天然压过个人规则：它坐 `prepend`，
个人规则坐 `user`，而**个人规则掀不翻任何一条 deny**（`allow` 规则的效力上限是把 `ask` 变成 `allow`）。

会话里用 `/permissions` 看当前生效的规则、每条来自哪一层、哪些工具被隐藏、哪些规则没生效。

**没有 `--yes` / 自动放行。** 托管策略里也不写 `allow`：策略说"不用问"会被当成自动放行开关，
与下面「安全」一节那条底线冲突 —— 守门器只在策略**更严**时才插手。
````

## 自查记录

写完计划后对着设计文档逐节核了一遍，下面四处偏离是**有意的**，且都比原稿更准：

1. **设计 §3.2 的形状少了两样，计划补上了。** 原稿给的是 `parseRule(text)` 与
   `Rule = { raw, tool, content? }` —— 但 `evaluate(rules, call)` 要"按行为分桶"，而 `Rule`
   里根本没有行为，桶无从谈起。计划改成 `parseRule(text, decision, home)` 并把 `decision`
   放进 `Rule`。`home` 也必须在解析期拿到，因为设计 §3.3 要求 `~` 展开，而 `Call` 里没有 home。
   归一因此落在**解析时**做一次（`content` 存的是已归一的形态），匹配时只归一调用侧 ——
   规则是启动期定下的，不该每次重算。

2. **设计 §6.1 的第 4 步守卫写反了。** 原文是 `!isLooser(p.decision, v1.decision) → return v1`。
   `isLooser(p, v1)` 是"p 比 v1 松"，取反就是"p 不比 v1 松" → 于是策略**更严**时不插手，
   策略**更松**时才插手。拿 `p=deny, v1=allow` 代进去：`isLooser(deny, allow)` 为假，
   `!假` 为真 → 返回 allow。这正是整个守门器要防的那条 fail-open。
   而 §6.1 里每一句说明、以及第 5 步那句 `heldNotice`（"策略里 X 要求 deny，实际得到 allow"）
   描述的都是相反的行为，所以 `!` 是笔误。计划按**意图**实现：
   `if (!isLooser(below.decision, policy.decision)) return below;`（下层比策略松才插手）。

3. **策略是 `allow` 时不插手 —— 这是计划对设计的一处收紧。** 按第 2 条修好守卫之后，
   `p=allow, v1=ask` 仍然会走进第 5 步（`isLooser(ask, allow)` 为真），于是策略的 allow
   会抹掉个人的 ask。那等于给策略文件开了一个自动放行开关，与用户明确的底线
   "谁加自动放行开关谁就是在开倒车"直接冲突。计划加了一条 `policy.decision === 'allow'` 直接返回。
   代价：策略作者没法用 `allow` 表达"这个不用问"；收益：守门器只可能让判定**更严**，
   与它自己的定位（防放宽）一致。

4. **设计 §1 表格里的 `stricter` 没实现。** 两条合并路径各自的三元表达式比一个通用比较器更直白
   （`permissions` 是"deny 时不许放宽"，`sec-default` 是"策略不是 allow 且下层更松时才拦"），
   留一个没人用的导出就是死码。真的需要时再加。

5. **`SourceInfo` 多了一个 `rules` 字段。** 设计 §8 的 `/permissions` 要给每条规则标出
