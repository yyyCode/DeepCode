# DeepCode P10 子代理的边界设计

> 对标 `docs/claude-code-架构分析/14-subagents.md`（下称 [14]）。那份文档的事实、依据与版本锚点
> 都在它里面，本文**不重述**，只写"我们缺什么、改什么、为什么、怎么验"。
>
> 一句话口径：**子代理的边界（它看得见哪些工具、它能派多深）今天由调用方按"会话的全部"算
> —— 边界画在插件里，于是嵌套一次就漏、换一条路径就没了。本阶段把这份面与这个数挪进内核，
> 按"当前这一轮"算。**

---

## 1. 出口标准（可验证，四条）

1. **嵌套不再把面拿回来**：父级那一轮的模型可见面是 `{Task, Read}` 时，它派出的子代理
   （省略 `tools`）拿到的就是 `{Task, Read}`，不是会话全部。探针 A 里那两条断言从此**反过来**
   （今天内层看得见 8 个 —— 错在外面）。
2. **深度上限对所有路径生效**：第三方插件直接 `$.agent.spawn` 的递归在第 4 层被**内核**拒
   （探针 B 今天抵达 6 层）。同一个数（3）在事实层只有一处，`Task` 与插件直派共用它。
3. **拒绝由内核给出、结果类型能表达它**：`AgentSpawnResult` 有 `{ ok: false; reason }` 分支
   （与 [14] 的 `{ deny }` 同形，`:218-219`）；理由里带名字链与上限数字；插件把它翻成工具层的
   一次 `deny`，屏幕表现与今天一致。
4. **三处口径收敛成一句**：README / 契约注释 / P4a 设计对"省略 `tools` 继承什么"说的是同一件事
   —— **继承父级那一轮的模型可见面**；P4a §6.1/§6.5/§8 里那句已经为假的断言有可追的更正。

任务级验收只跑 `pnpm typecheck`；测试按检查点批量做（用户长期指令：一次校验多个任务）。

### 2.1 两个已经实测出来的洞（不是读代码猜的）

写这份设计之前，先拿两个探针在真 `createEngine` + 真 `runTurn` 上跑了一遍
（`test/zz-tmp-probe.test.ts`，跑完即删，结论记在这里）。

**探针 A —— 嵌套一次，被扣掉的面就回来了。**

两个 agent：`outer`（`tools: ['Read', 'Task']`）、`inner`（省略 `tools`）。会话模型先派 `outer`，
`outer` 的模型再派 `inner`。记录每一轮请求里带的工具：

```
探针A｜外层那一轮看见: ["Task","Read"]                                            ← 2 个，白名单生效
探针A｜内层那一轮看见: ["Task","Skill","Read","Write","Edit","Bash","Glob","Grep"] ← 8 个，会话全部
```

`inner` 的 `tools` 是省略的，于是 `resolveTools` 走 `spec.tools ?? $.tool.list()`
（`cli/subagents.ts:203`）—— **`$.tool.list()` 是会话的注册面，不是父级这一轮的面**。
P4a 设计 §6.5 那句「没有任何一条路径能通过子代理拿到父级拿不到的东西。**这不是一条要人去守的
规则，是结构**」在**嵌套**这一格上是**假的**：一个被限制成"只读 + 可派"的 agent，只要派出一个
没写白名单的 agent，就把整套工具拿回去了。

**探针 B —— 深度保险丝只装在一条路上。**

一个第三方插件（`uses` 里有 `agent`）在自己的 `tool.call` 里直接调 `$.agent.spawn`，
内层的模型再调同一个工具：

```
探针B｜实际到达的层数: 6 （Task 那条路径的上限是 3）
探针B｜一共发生了几次模型请求: 13
```

6 不是"上限"，是"脚本给多少就走多少"。`MAX_DEPTH = 3` 写在 `cli/subagents.ts:20`、
检查也在那儿（`:113`）—— **插件直派这条路一次都没经过它**。[14] 启示 11 说的正是这个形状：
「限额必须显式定义并**同时施加于前后台两条路径**」，并且它自己栽过
（`CHANGELOG.md:4347`：前台路径一度比后台松）。我们只有一条路径，却已经把它装错了地方。

**两个洞是同一件事的两半**：`面`与`深度`都是"内核对**当前这一轮**知道的、而调用方按
**会话全部**猜的"。所以本阶段不做两个补丁，只做一件事 —— 把这两样挪进内核。

## 3. 逐项设计

### 3.1 「面」是什么：模型这一轮看得见的那一份

先把话说死（这也是三处口径收敛后的那一句）：

> **一个子代理默认继承的，是"父级那一轮模型看得见的工具"，不是"会话注册过哪些工具"。**

「模型看得见的」就是 P9 那个唯一算法 `listTools`（`core/tool-list.ts`）的产物 ——
注册面再过三道（本次白名单 / `hidden` / 有注册描述）。于是这句话顺带修掉一个残余：
被权限规则整工具隐藏的、以及没注册描述的**故障**工具，从此也不进子代理的面。方向是**更严**，
与 P4a §6.5 想说的是同一个方向。

（诚实一句：主循环自己仍然没有白名单那一层 —— 它 `ctx.tools === undefined`（`core/loop.ts:383`），
所以模型点名一个被隐藏的工具仍会走到 `tool.check` 那里被规则拒。父子这一条**不对称**，
方向是子代理更严。）

### 3.2 白名单改成「声明」，解析归内核

今天 `AgentSpawnRequest.tools` 是**已解析**的清单（`contract/agent.ts:51`），解析在插件里
（`cli/subagents.ts:202-207` 的 `resolveTools`）。这个分工有一个前提，而那个前提是错的：
**它假设调用方知道"父级这一轮的面"** —— 调用方不知道，它只知道会话的注册面。

改成声明：

```ts
export type AgentSpawnRequest = {
  readonly name: string;
  readonly systemPrompt: string;
  readonly task: string;
  /** 只许这些。省略 = 继承父级那一轮的面。内核拿它与父面**求交** —— 它只会更小，不会更大。 */
  readonly allow?: readonly string[] | undefined;
  /** 在白名单之上再扣一层。 */
  readonly deny?: readonly string[] | undefined;
  readonly model?: string;
  readonly maxHops?: number;
};
```

内核按下式解析（三行，一个地方）：

```
父面   = 栈顶 ?? 会话的模型可见面（listTools 的产物）
请求面 = allow === undefined ? 父面 : 父面 ∩ allow
这一轮 = deny  === undefined ? 请求面 : 请求面 \ deny
```

**`allow` 是求交，不是替换** —— 这是本阶段唯一一处语义变化，也是出口标准一。
`tools: []` 仍然是"一个工具都没有"，于是"连 `Task` 都没有 ⇒ 递归从结构上断掉"
这条性质原样保留（P4a §8）。

被交集丢掉的每一个名字打一条 `debug`（`$.logger.debug`）：这正是 [14] 启示 3 要的那种
"可诊断手段"的最低配 —— 一个 agent 明明写了 `tools: ['Bash']` 却调不通时，读日志能看见
"Bash 不在父级那一轮的面里"。

### 3.3 面栈与深度：把"当前这一轮"变成内核知道的事实

内核（`core/nouns/agent.ts`）在每次 `spawn` 里维护一个**面栈**：

- 栈里每一格 = 一层**正在跑的 loop** 的模型可见面；栈底那一格由内核按 `listTools` 算出来
  （会话这一层没有白名单，所以它等于"模型看得见的全部"）。**栈的长度 = 现在正在第几层。**
- 解析出的"这一轮的面"算完就 **push**，`runTurn` 跑完在 `finally` 里 **pop**
  （名字栈与它同生共死，用来在拒绝消息里说清"谁派的谁"）。
- **深度上限 = 栈的深度**（`MAX_DEPTH = 3` 从 `cli/subagents.ts:20` 搬来，那儿删掉）。
  判定与措辞都在内核：`嵌套太深了（scout → explorer → scout → scout，上限 3 层）`
  —— 与今天一字不差。
- 于是**所有路径**（`Task`、插件直派、将来任何新入口）走的是同一个数、同一个函数。

`model` / `maxHops` / `signal` / 静音那一层一个字不动。

**为什么是栈，而不是"把父面当参数传下去"**：插件调 `$.agent.spawn` 时手上没有父面的任何线索
（`$` 是引擎全局的），父面只存在于"此刻跑着的那几层 loop"里 —— 栈是这份事实的唯一载体。
**已知代价**：一个插件若用 `Promise.all` 并发派两个子代理，两边的 push/pop 会交错、层级会被
算错。今天没有并发路径（工具串行执行，`core/loop.ts`），记进 §5；真要并发，那时该上的是
`AsyncLocalStorage`，而不是把栈改成别的形状。

### 3.4 结果类型：拒绝要能被表达

拒绝从此由**内核**给出（深度是内核的事实），所以结果类型必须能表达"这次没跑"。
[14] 里 `$.agent.spawn` 正是这么写的（返回 `{ model, agentId }` **或 `{ deny }`**，`:218-219`）
—— 这是本阶段唯一一处"与它同形"的加法：

```ts
export type AgentSpawnResult =
  | {
      readonly ok: true;
      readonly text: string;
      readonly stopReason: TurnReason;
      /** 这是第几层（栈长度）。1 = 会话直接派的。 */
      readonly depth: number;
    }
  | { readonly ok: false; readonly reason: string };
```

`depth` 是白送的（栈长度已经在手上）：调用方与遥测从此知道"这是第几层"，不必自己数。
它**不是**句柄 —— 没有 id、没有"之后再来取"，因为前台同步下没有"之后"。

插件把 `{ ok: false }` 翻成工具层的一次 `deny`（`{ deny: reason }`），屏幕表现与今天一致
（`activity` 那条 `⛔ 拒绝 —— …`）。

### 3.5 事件：`agent.spawn` 带上 `depth`

`agent.spawn` 今天报 `{ name, task, model? }`（`contract/events.ts:111`）。
加一个 `depth: number`（**必填**：内核永远知道它）。

理由不是"顺手"：出口标准二那句话（"所有路径共用同一个数"）需要一个**可观测**的出口，
否则验它只能读代码；`mods/telemetry` 已经订阅这个事件（`mods/telemetry/index.ts:119`），
它今天记的是 `{ agent }`，看不出嵌套 —— 加上 `depth` 之后，一次递归在遥测里是**可见**的。

代价：这是**契约变宽**（事件 args 多一个必填字段）。受影响的是两处手写 dispatch 的测试
（`test/dispatch.test.ts:388`、`mods/telemetry/test/plugin.test.ts:92`），各加一个 `depth: 1`。
第三方插件不吃 args，一行不用改。

**这条出口还有一个顺带的用处**（写设计时没想到，施工时用上了）：进度提示「派子代理 X」从
`tool.call` 里**改挂到这个事件上**。理由是内核只对**真要开跑**的那一次派它（深度超了的那次在
它之前就返回），而插件在调 `spawn` 之前无从知道 —— 挂在 `tool.call` 上的话，被拒的那次屏幕上会
留下一行"派子代理 X"、永远不回来。挂在事件上的两个好处：那一行与 P10 之前**一字不差**，
而且**插件直派**的子代理也被照亮了（那条路径上没有 `Task`，原先没有任何地方出声）。
见 §5 偏差 5。

## 4. 明确不做（十一条）

1. **句柄式委派与后台**（[14] 的 D1/D2，它的整个 A 节）。README 已经记过这一条：要做得先有
   "能等的东西"。本阶段不碰 —— 但**记一笔**：一旦有了后台，§3.3 的面栈必须跟着改成按 loop
   分槽（或上 `AsyncLocalStorage`），因为那时"当前这一轮"不再是全局唯一。
2. **名册与点对点消息**（`$.agent.list()` / `SendMessage` / `TaskOutput` / `TaskStop`）。
   前台同步下一次派发就是阻塞到它跑完，"运行中的代理"不是一个可以被寻址的对象。
   等第 1 条做了再一起做 —— 这是**同一条依赖**，不是四个独立的漏项。
3. **交付的语义分类**（`send`/`flagged`/`withheld`）。它解决的是"子代理读过外部内容后，
   它的答复是不可信输入"。我们的外部内容只有 `Read`/`Bash` 两条路（没有网络工具），
   面窄得多；真正的注入防护该落在"外部内容进上下文"那一处，不是委派边界。
   **记偏差，不假装做了。**
4. **`context: fork`**。[14] 启示 12 说的"别做两套运行时"我们已经成立（只有一个 `runTurn`）；
   缺的是让技能声明"跑在 fork 里"。不追的理由：技能正文是**知识**，把它加载进当前上下文
   正是 `Skill` 工具的用途；fork 的收益（隔离）在这里没有对应的问题。
5. **模型解析的第三层**（会话默认子代理模型）。加一个只服务一个场景的设置键，
   不如让 agent 文件自己写 `model`。
6. **`omitClaudeMd` 这类"让它继承指令文件"的旋钮**。我们今天是**硬隔离**：子代理的 system
   prompt 只有 `spec.prompt`（或回落的那份基础提示），`AGENTS.md` 一个字都不进 ——
   比它的默认更严，代价是**子代理不知道项目规矩**。这条代价进 README 的已知限制；
   旋钮等真有需求再说（加它必然是**放宽**，与本阶段方向相反）。
7. **`isolation: worktree | remote`**。没有 worktree 管理，也没有远程会话。
8. **`memory: user|project|local`**。跨 run 的持久记忆是隔离的**受控例外**，它需要
   "记忆住哪儿、谁清理、怎么和既有的 `store` 名词分工"三件设计，这里一件都没有。
9. **`Origin` 上加一个"这是第几层"的字段**（对标 `BaseHookInput.agent_id`）。今天唯一的推断方
   `cli/activity.ts:41-49` 在**串行执行**这个前提下推得是对的（一次只有一个 `Task` 在跑），
   所以没有消费者；改 `Origin` 是每个 hook 都能看见的契约变宽，留给"有了后台委派、
   推断失效"的那一阶段。
10. **并发上限**。工具串行 ⇒ 并发天然是 1。
11. **`SubagentStart` / `SubagentStop` 两条 classic hook**。它们的价值在"子代理有自己的
    生命周期"，而子代理的每一轮本来就派 `turn.start`/`turn.complete`；加一个配对的
    `agent.stop` 事件是给一个不存在的消费者开第 40 个事件。

## 5. 偏差与代价（预先登记，做完逐条核对）

1. **`spec.tools` 的效力变了**：它从"绝对白名单"变成"**父面的子集**"。一个写着
   `tools: ['Bash']` 的 agent，若父级那一轮看不到 `Bash`，它拿到的就是**空面**。
   这是出口标准一，也是本阶段唯一可能让人"咦"一下的行为变化 —— README 与 CHANGELOG 都要说。
2. **"省略 `tools`"的继承对象变了**（会话注册面 → 父级那一轮的模型可见面）。对**第一层**
   几乎等价（差别只在被隐藏与没注册描述的工具），对**嵌套层**完全不同。
3. **`agent.spawn` 的事件多一个必填 `depth`** —— 契约变宽，两处手写 dispatch 的测试跟着改。
4. **`AgentSpawnResult` 从平坦结构变成判别式联合** —— 契约变更，消费方要按 `ok` 分支
   （今天只有一个消费方：`cli/subagents.ts`）。
5. **`$.ui.notice` 的措辞变了**：派下去那一刻还不知道层数（层数由内核在 `spawn` 里定），
   于是「派子代理 scout（第 N 层）」变成「派子代理 scout」，`第 N 层`挪到回来那一条
   （`子代理 scout 回来了（end_turn，第 2 层）`）。
   —— 执行时发现"派子代理 X"那一条不该由插件在**调 `spawn` 之前**打：内核只对**真要开跑**
   的那一次派 `agent.spawn`（深度超了的那次在它之前就返回），插件却无从知道。第一版挪过来
   之后，被拒的那次屏幕上会留下一行"派子代理 X"、永远不回来 —— 那是假账。
   于是那条通知**挂在 `agent.spawn` 上**（子代理插件订阅自己的事件，只读、不改裁决）。
   顺带的好处：插件直派的子代理也被照亮了（那条路径上没有 `Task`，原先没有任何地方出声）。
   屏幕上"派子代理 X"这一行与 P10 之前**一字不差**。
6. **派一次子代理会多算一遍工具面**（`tool.describe` 多派一轮）。内核要先知道"父级这一轮
   的面"，而会话那一层没有白名单，于是那一次是**全量**的一遍 —— 与会话主循环每一轮做的是
   同一件事，只是这里多做一回（`test/subagent.test.ts` 的 C2-5 原先钉的是"describe 恰好
   三次"，跟着改了：次数是实现细节，"模型看见什么"才是承重的那条）。
   代价只在描述（`tool.describe` 是纯查询，多答一次的插件不会被谁误解），不在权限
   —— 被挡下的名字照样进不了内层的面，一次 `tool.call` 都到不了。
7. **面栈在并发 spawn 下会错位**（§3.3）。今天不可达。
8. **`resolveTools` 这个函数删掉**，连带 P4a §6.1 那段"三条规则在插件里解析"的说明。
   设计文档不改历史，只加更正指引（T5）。
9. **"子代理答偏了"仍然看不出来**（[14] 启示 3 要的"可诊断手段"只做到 debug 一条）。
   今天能给的只有：调用的 prompt + 它最后一段话。写进已知限制。
