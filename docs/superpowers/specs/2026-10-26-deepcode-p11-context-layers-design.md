# DeepCode P11 上下文五层分级压缩设计

> 对标 Claude Code 的上下文窗口管理（用户提供的「压缩五步走」材料，
> 以及 `docs/claude-code-架构分析/11-memory-and-context.md`）。
> 一句话口径：**能不压就不压；必须压时，从最轻的手段开始加码。**

---

## 1. 现状与差距

P7 只落地了第 5 层：

| 层 | 复刻对象 | DeepCode 现状 |
| --- | --- | --- |
| 1 大结果存磁盘 | 单结果 > 50KB 落盘，消息里留 2KB 预览；单条消息总量 > 200KB 继续外置 | 无。`Read` 只截断到 2000 行，`Bash` 截断到 40000 字符，截掉的部分**没有存盘**，模型再也拿不回来 |
| 2 砍掉远古消息 | 移除开头一批旧消息 + 边界标记，零 API 开销 | 无。只有第 5 层「保留最近 N 轮」 |
| 3 清理老工具输出 | 只清可重新获取的工具结果（Read/Bash/Grep/Glob/...），保留最近 N 个 | 无 |
| 4 读时投影 | 达到 90% / 95% 时分段压缩，**不改原始历史**，只改这一次请求 | 无 |
| 5 全量摘要 | 到阈值后一次摘要替换整段历史 + 压缩后恢复 | 已有：`cli/compact.ts`，含三重断电器、`/compact <说明>`、摘要即一条消息 |

差距不是「压缩算法不够好」，而是**压力全压在最后一层**：一旦到阈值，直接从「完整历史」
跳到「一段摘要」，中间四道更便宜、信息损失更小的闸都不存在。

## 2. 五层阶梯（本阶段的口径）

| 层 | 手段 | 信息损失 | API 开销 | 触发 | 本阶段落点 |
| --- | --- | --- | --- | --- | --- |
| 1 | 大工具结果落盘，消息里留预览 | 几乎为零（全文在磁盘，可再读） | 零 | 单结果 > 50K 字符；单条 tool 消息总量 > 200K 字符 | `core/context-shaping.ts` + `cli/context-window.ts` |
| 2 | 砍掉远古消息，边界标记 | 低（旧对话不在本次请求里，转录仍在） | 零 | 估算 ≥ `atTokens × 80%` | 同上（读时投影） |
| 3 | 清空老工具结果 | 中低（可重新读/重新跑） | 零 | 估算 ≥ `atTokens × 85%` 或距上次请求 ≥ 60 分钟 | 同上（读时投影） |
| 4 | 分段摘要投影 | 中 | 低（每段一次摘要） | 估算 ≥ `atTokens × 90%`；≥ 95% 时保留更少轮次 | 同上（读时投影） |
| 5 | 全量摘要 | 高 | 高（一次摘要） | 实测 ≥ `atTokens`（现有断电器不变） | `cli/compact.ts`（不改形状） |

### 2.1 为什么第 2–4 层做成「读时投影」

复刻对象的第 2、3 层是**写时压缩**：直接改消息列表。我们在 P11 里把 2–4 层统一做成
**读时投影**（只在调用 API 前计算一份视图），理由有三条：

1. **不重写历史**。转录是 append-only（架构文档 L2 层），读时投影让「盘上的完整对话」
   与「这次发出去的视图」彻底分开。用户 `--resume` 接回来的仍是完整历史。
2. **不会破坏 tool_use / tool_result 配对**。写时删消息最容易造出「有 tool_use 没有
   tool_result」的非法消息；投影在每次请求前从完整历史重新算，切点固定在轮边界，天然安全。
3. **第 4 层本来就是读时投影**。把 2、3 层也放进同一个投影函数，三层的顺序、减负、
   统计都只有一处。

代价：每次请求都要重算一遍（纯字符串操作，零 API）；触发层时请求前缀会变，
可能打断 provider 侧的隐式 prompt cache。这一条记在 §7 偏差里。

### 2.2 阈值为什么用 `atTokens` 的比例

我们没有模型注册表，不知道模型窗口是多少（P7 §3.1 已经如实声明）。所以**不发明窗口**：
第 2–5 层的阈值全部锚在用户已经配置的 `compact.atTokens` 上，按比例排成阶梯。
`atTokens` 默认 100K 只是一个占位值——它本来就被标注为「猜的」（`cli/settings.ts`）。

## 3. 架构

```
                每次 provider.stream 之前
                          │
   messages（完整历史） ──┼──► project()
                          │      1. 估算本轮请求 token
                          │      2. 第2层：snip 远古轮次
                          │      3. 第3层：清空老工具结果
                          │      4. 第4层：old head → 摘要 → 投影
                          │      5. 返回 messagesForQuery（不改 messages）
                          ▼
                    provider.stream(messagesForQuery)

  工具结果进入消息列表之前
                          │
   runOneTool() ──────────┼──► absorbToolResults()
                          │      第1层：>50K 落盘，预览替换
                          ▼
                    messages.push({ role: 'tool', results })

  一个 turn 收尾之后
                          │
   turn.complete.usage ───┼──► Compactor.afterTurn()
                          │      第5层：实测 ≥ atTokens 才摘要
                          ▼
```

关键协调点：**第 2–4 层是投影，所以端点报回来的 `input_tokens` 已经反映了它们的效果。**
现有压缩器吃的就是这条实测用量（`onUsage` → `compactor.note`）。于是：

- 投影把上下文压到阈值以下 → 第 5 层不触发（不需要显式的 `tokensFreed` 传递）；
- 投影也压不下去 → 第 5 层照旧触发，断电器一条不改。

这就是「每一层为下一层减负」在 DeepCode 里的落法。

## 4. 逐层设计

### 4.1 第 1 层：大工具结果落盘

**常量**（`DEFAULT_CONTEXT_LAYERS`）：

| 字段 | 值 | 说明 |
| --- | --- | --- |
| `toolResultMaxChars` | 50 000 | 单个结果超过就外置 |
| `toolResultPreviewChars` | 2 000 | 留在消息里的预览长度 |
| `toolMessageMaxChars` | 200 000 | 同一条 `role:'tool'` 消息的总字符上限；超了继续外置最大的 |

**落点**：

- `core/context-shaping.ts` 的 `externalizeLargeResults(results, names, config, write)`：
  纯选择逻辑 + 可注入的写盘回调（测试与 benchmark 不碰磁盘）。
- `cli/context-window.ts` 提供写盘回调：`<home>/.deepcode/projects/<slug>/tool-results/<sessionId>/<toolUseId>.txt`。
- 预览正文：
  `[大工具结果已存盘] 完整内容 N 字符，存于 <path>。下面是前 2 000 字符；需要后续内容时用 Read 读这个文件（offset / limit）。`

**恢复路径**：`Read` 工具补 `offset` 参数。在此之前只能重读前 2000 行，预览里说「读特定行范围」
是一句空话。这是第 1 层能成立的前提，不是顺带的功能。

**失败方向**：**fail-open**。写盘失败 = 保留原结果 + 提醒一次（不静默、不丢内容）。
上下文管理失败不允许把一个正在跑的 turn 弄挂。

### 4.2 第 2 层：砍掉远古消息

**算法**：从尾部数第 `snipKeepTurns`（默认 6）条 `role:'user'` 消息，切点之前的整轮全部移除。
边界标记**合并进切点后的第一条 user 消息**，避免连续两条 user 消息：

```
[上下文清理] 更早的 N 条消息已不在本次请求里（完整历史仍在转录）。以下是最近 6 轮：

<原来的那条 user 消息>
```

**为什么合并而不是单插一条**：这个项目的端点兼容经验里，连续两条 user 消息是「某些端点会拒」
的形状（`cli/repl.ts` 的注释）。摘要消息（第 5 层）目前是单插的，那是既有形状；新加的层
不复制这个风险。

**保护**：切点必须落在轮边界（user 消息上），绝不切出一个孤立的 tool_result。

### 4.3 第 3 层：清理老工具输出

**可清理集合**（与复刻对象同形）：

```
Read, Bash, Grep, Glob, WebSearch, Write, Edit
```

共同点：**结果可重新获取**。`Task` / Agent 类工具的结果不清 —— 子代理的推理过程不可重复。

**算法**：收集所有可清理的工具结果，保留最近 `microKeepRecent`（默认 5）个，
其余内容替换为 `[旧工具结果已清理]`。`isError` 置 `false`（旧错误不再当成本轮失败信号）。

**触发**：估算 ≥ `atTokens × 85%`，**或**距上一次请求 ≥ 60 分钟。
后者对应复刻对象的「时间衰减」：缓存大概率已过期，此时清老结果不会浪费缓存投入。

### 4.4 第 4 层：读时投影

**触发**：估算 ≥ `atTokens × 90%`；达到 95% 时进入「紧急」模式，保留更少轮次
（默认 4 轮 → 2 轮）。

**算法**：

1. 在轮边界切出 `head`（更早的消息）与 `tail`（最近 N 轮原文）。
2. `head` 交给摘要器，要求只写：目标、改过的文件、结论、未决问题，不复述过程。
3. 用一条摘要消息替换 `head`，并与 `tail` 的第一条 user 消息合并。
4. **只返回投影，不改 `messages`。**

**缓存**：摘要按 `sha1(JSON.stringify(head))` 缓存。同一段 head 只摘要一次；
head 变了才重新算。命中缓存的投影照样生效，但不重复计入「折叠 N 段」。

**失败方向**：**fail-open**。摘要调用失败 / 返回空 / 投影没有更短 → 这一层整层跳过，
保留完整视图并提醒一次。宁可让第 5 层去处理，也不静默丢掉一段历史。

### 4.5 第 5 层：全量摘要（不改）

`cli/compact.ts` 的形状、断电器、`/compact <说明>`、摘要即一条消息，全部不动。
P11 只改它**什么时候被调用**：第 2–4 层把请求压下去之后，`turn.complete` 报的输入
token 变小，`afterTurn` 自然不触发。这条由集成测试钉住。

## 5. 配置

新增可选的 `compact.layers`（字段级降级，与现有 `compact` 一致）：

```json
{
  "compact": {
    "auto": false,
    "atTokens": 100000,
    "keepTurns": 6,
    "layers": {
      "toolResultMaxChars": 50000,
      "toolResultPreviewChars": 2000,
      "toolMessageMaxChars": 200000,
      "snipAtRatio": 0.8,
      "snipKeepTurns": 6,
      "microAtRatio": 0.85,
      "microKeepRecent": 5,
      "microIdleMs": 3600000,
      "collapseAtRatio": 0.9,
      "collapseUrgentRatio": 0.95,
      "collapseKeepTurns": 4,
      "collapseUrgentKeepTurns": 2
    }
  }
}
```

校验：字符数是正整数；比例在 `(0, 1]`；`preview < max`；比例阶梯必须单调递增
（`snip ≤ micro ≤ collapse ≤ urgent`）。违反的**单字段**按默认值处理并出声，不废掉整份文件
（它不是权限，没有「猜严/猜松」的方向问题）。

## 6. 可观测性

`/context` 新增一行（在「上次实测」之前）：

```
  分层压缩　外置 2 个（会话累计） · 清理 14 条旧消息 · 清空 7 个旧工具结果 · 折叠 1 段 · 上次请求 96,400 → 61,200 token
```

- 「外置」「折叠」是**会话累计**，且折叠只数**真的生成过摘要**的段：命中缓存的重复投影
  只应用、不重复计数（否则同一段历史会被数成几十段）。
- 「清理」「清空」与「上次请求 before → after」是**上一次请求**的投影结果。
- 数字全部来自投影器自己，不另算一本账。

第 1 层落盘的文件路径不隐藏：预览正文里写着，`/context` 不重复列。

## 7. 偏差与代价（如实写）

1. **第 2、3 层不是写时压缩**。复刻对象直接改消息列表；我们做读时投影。对外效果
   （请求 token 变少）相同，但转录保留完整历史。代价是每次请求都要重算。
2. **阈值是比例，不是复刻对象的绝对窗口**。复刻对象按「模型窗口 − 输出预留 − buffer」
   算绝对阈值；我们没有模型注册表，只能锚在 `compact.atTokens` 上。`atTokens` 本身是猜的，
   这条偏差继承自 P7。
3. **第 4 层每段摘要仍要一次 API 调用**。比第 5 层便宜（只压 head，不压最近轮次），
   但不是零。
4. **请求前缀会在跨阈值时变化**，可能打断 provider 侧的隐式 prompt cache。这是所有
   写时 / 读时压缩共有的代价；复刻对象用「重算优于搬运 + 缓存稳定性清单」兜住，我们只做到
   「投影结果是确定性的、同一段历史同一份摘要」。
5. **第 1 层落盘目录没有清理策略**。复刻对象有 1GB 封顶；我们暂时只按会话分目录。
   长会话会累积文件 —— 记在这里，不是忘了。
6. **第 4 层不恢复文件状态**。复刻对象的 Post-Compact Restoration 会重新注入最近 5 个文件；
   我们依赖「每轮重算系统提示 + 模型自己重新 Read」。不做自动恢复，是因为我们的
   `fileStateCache` 不存在，凭空造一个会多一条存储线。
7. **第 1 层是写时的，所以转录里存的是预览而不是全文**。全文在
   `tool-results/<会话>/<工具调用>.txt`，路径就写在预览里；`--resume` 接回的是预览 + 路径，
   模型需要时自己 `Read`（`offset` / `limit`）。为什么不让第 1 层也做读时投影：那样每次请求
   都要把全文再读一遍、再算一遍预览，省下的磁盘换成了每轮的 IO —— 不划算。

## 8. 验收

### 8.1 出口标准

1. **五层都在**：第 1–4 层有单元测试；第 5 层原有测试一条不改仍然全绿。
2. **顺序与减负**：同一份压力历史，逐层套用后 token 单调下降；benchmark 里分层策略的
   第 5 层摘要次数为 0（基线的 1–9 次），第 2–4 层把请求压到 `atTokens` 以下之后，
   第 5 层自然不再触发。
3. **不破坏历史**：第 2–4 层执行后，传入的 `messages` 数组逐字节不变。
4. **失败方向**：写盘失败保留原结果；摘要失败跳过第 4 层；两种情况都出声且不抛。
5. **可恢复**：第 1 层外置的文件能用 `Read` 的 `offset` / `limit` 读回指定行范围。
6. **benchmark 可复现**：`pnpm bench` 输出 Markdown 表；测试断言分层策略在三个场景下
   峰值请求 token 与全量摘要次数都不劣于「只有第 5 层」。
7. **接线**：`runTurn` 把投影视图交给 provider，工具结果先过外置再进消息列表；投影抛错时
   回退完整历史。这三条由 `test/loop-options.test.ts` 的脚本化 provider 钉住。

### 8.2 Benchmark 场景

| 场景 | 形状 | 实测（`pnpm bench`） |
| --- | --- | --- |
| `huge-reads` | 15 轮，每轮一次 80K 字符 Read | 第 1 层外置 15 个；峰值 140,062 → 8,344（−94.0%）；第 5 层摘要 9 → 0 次 |
| `long-session` | 40 轮，每轮 4K Bash 输出 | 第 2 层命中 17 次；峰值 30,168 → 23,128（−23.3%）；第 5 层摘要 1 → 0 次 |
| `mixed` | 30 轮，每 5 轮一次 60K Read，其余 1K | 第 1 层外置 6 个；峰值 32,080 → 9,474（−70.5%）；第 5 层摘要 9 → 0 次 |

三个场景统一取 `atTokens = 30,000`（阈值本身是猜的，benchmark 只是把它固定下来好比较）。
基线 = 「不做 1–4 层，只在 `atTokens` 处做全量摘要」。数字来自 2026-10-26 的 `pnpm bench`；
token 是 `ceil(chars/4)` 估算，系统提示与工具清单按 0 算，摘要正文用固定短文本 ——
量的是请求体积与调用次数，不是摘要质量。

**一个实测发现：第 3 层在三个场景里 0 命中。** 原因不是它没接上，而是顺序：
第 2 层先切，切完通常已经低于 85%，第 3 层按比例就不会再触发。第 3 层真正的主战场是
「轮次少、结果多」（切点不存在，第 2 层无从下手）和「闲置 60 分钟」（缓存已过期）。
这两条分别由 `microCompact` 单测和 `context-window` 的闲置触发单测钉住。如果以后想让它
在比例阶梯上更常出手，改的是顺序或阈值，不是实现 —— 这里如实记下，不假装它每次都在干活。
